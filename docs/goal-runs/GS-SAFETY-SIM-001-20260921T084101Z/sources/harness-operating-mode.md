# raphthon — 6~12시간 대규모 병렬 운영

[전체 구조](./README.md) · [역할 설명](./roles.md) · [업무 절차](./harness.md) · [R&R](./responsibilities.md)

이 문서는 하네스의 운영 전제를 정의한다. 목표 실행 플랫폼의 이름은 사용자가 지정한
**raphthon**으로 유지한다. 플랫폼 구현이나 수백 개 동시 실행을 이미 검증한 문서가 아니다.

## 1. 가장 중요한 원칙

**토큰을 적게 쓰는 작은 팀이 아니라, 가능한 최대 규모의 에이전트가 6~12시간 동안
병렬로 일하며 조사·대안 제작·통합·검증·개선을 반복하는 품질 우선 팀이다.**

- 실행 규모: 실제로 허용되고 운전 가능한 최대 동시 인원 활용.
- 실행 시간: 한 번의 가동 목표를 6~12시간 범위에서 지정.
- 평가 우선순위: 목표 충족, 디자인 완성도, 구현 정확성, 검증 강도와 전체 일관성.
- 비용 정책: 토큰 비용 절감이나 최소 호출 수를 최적화 목표로 삼지 않음.
- 역할 정책: 같은 역할의 복수·대량 동시 실행 허용.
- 범위 정책: 최대 병렬화가 사용자 승인 없는 새 기능·외부 작업까지 허용하는 것은 아님.

초기 기능이 동작한다고 곧바로 끝내지 않는다. 남은 가동 시간에는 승인된 목표 안에서
대안 비교, 세부 디자인, 빠진 경우, 성능, 독립 검증과 회귀 확인을 계속 개선한다.
단, 시간을 채우거나 인원수를 자랑하기 위한 무관한 작업은 만들지 않는다.
더 할 품질 작업이 정말 없다면 근거를 보고하고 조기 인계를 제안한다.
사용자의 중지·취소와 실제 권한·계정 한도는 언제나 우선한다.
승인된 기획·컨셉·기술 계약은 더 좋은 결과를 만들겠다는 이유만으로 다시 결정하지 않는다.
대안은 업무 카드에서 허용한 범위 안에서 제작한다. 기준 변경은 R&R의 승인 절차를 따른다.

## 2. 책임자 수와 작업자 수는 다르다

고정 책임은 10개지만 작업자는 훨씬 많을 수 있다.
작업자 생성 요청마다 별도의 역할 이름을 새로 만들 필요는 없다.
같은 역할에 서로 다른 작업 ID·후보 ID·소유 영역을 준다.

| 역할 | 같은 역할을 대량으로 나누는 기준 |
| --- | --- |
| 서브 리서처 | 주제·언어·출처·부품·가설·독립 교차 확인 |
| 서브 기획자 | 사용자 스토리·정책·예외·흐름·대안 |
| 웹·모바일 디자이너 | 스토리·화면·상태·화면 크기·시안 후보 |
| Blender 디자이너 | 자산·부품·장면·재질·움직임·조명 후보 |
| FE·BE·Mobile 개발자 | 기획 항목·기능·화면·모듈·서로 다른 구현 후보 |
| 서브 QA | 목표·화면·시나리오·환경·보안 관점·독립 재검증 |

작업자로 추가되는 취합·통합 담당자도 기존 Lead의 책임 안에서 실행된다.
이를 이유로 고정 조직의 이름과 책임자를 계속 늘리지는 않는다.

## 3. 같은 역할의 “중복”은 두 가지다

**분담형 중복:** 같은 역할의 여러 작업자가 서로 다른 부분을 동시에 만든다.
예를 들어 FE 개발자들이 로그인, 검색, 목록, 상세, 결제 등 기능을 나누어 구현한다.

**비교형 중복:** 같은 과제를 여러 작업자에게 독립적으로 맡겨 더 좋은 결과를 고른다.
예를 들어 같은 상세 화면을 공통 컨셉 안에서 서로 다른 디자이너들이 제안한다.

두 방식 모두 허용하고 적극 활용한다. 비교형 결과는 후보별 공간에 분리한다.
담당 Lead는 기준에 따라 후보와 조합안을 추천하고, QA만 결과의 합격 여부를 판정한다.
합격한 후보 중 선호 선택은 기존 역할의 결정 범위에서 한다. 조합한 결과는 새 후보로 재검증한다.
다수결이나 에이전트 수 자체가 정답의 증거는 아니다.

## 4. 디자이너 수십·수백 명이 같은 방향으로 일하려면

UI 디자이너 Lead는 제작 전에 공통 컨셉 묶음을 정한다.

- 사용 목적과 대상 사용자, 원하는 인상과 참고 방향.
- 색상·글자·간격·구성 요소·상태 표현의 공통 기준.
- 스토리와 화면 사이의 연결, 일관되게 반복할 패턴.
- 3D 작업의 크기·좌표 방향·재질·파일 전달 조건.
- 바꿔도 되는 부분과 반드시 유지할 부분, 기준 버전.

디자이너들은 같은 묶음을 받아 스토리·화면별로 대량 병렬 작업한다.
컨셉 변경은 담당 Lead의 변경 요청·관련 협의·필요 승인을 거친 뒤 버전을 올린다.
Orchestrator는 승인된 변경의 영향 작업만 갱신한다.
화면군·자산군별 취합 담당자는 연결과 일관성의 사전 점검 자료를 모으고,
UI 디자이너 Lead는 전체 방향과 중요한 차이에 대한 의견을 낸다. 결과 승인은 QA가 맡는다.

예시로 여러 스토리의 각 화면마다 복수 후보를 병렬 제작할 수 있다.
후보 수를 작은 고정값으로 제한하지 않고 검증 가능한 비교 범위와 실제 가용 자원에 맞춰 확대한다.

## 5. FE 개발자 수백 명을 동시에 운영하려면

Frontend Lead는 공통 컴포넌트·라우팅·상태·API·디자인 기준을 먼저 공유한다.
각 작업자는 특정 기능과 수정 가능한 영역을 받는다.
단위는 사람 이름이 아니라 결과를 확인할 수 있는 작업이어야 한다.

- 각 쓰기 작업자는 검증된 별도 checkout/worktree 또는 동등한 격리 공간을 사용한다.
- 분리되지 않은 공유 폴더에서 수백 명에게 동시에 쓰기를 허용하지 않는다.
- 공통 파일 변경은 소유 담당자를 정하거나 변경 요청을 통해 조정한다.
- 기능군별로 결과를 취합하고, 통합 후보에 자동 검사와 독립 QA를 적용한다.
- 서로 다른 구현 후보는 같은 기준으로 Lead가 추천하고 QA가 판정하며 무작정 병합하지 않는다.
- 공통 계약 변경이 승인되면 새 버전의 영향 작업과 검증을 다시 배정한다.

작업 공간만 나눠도 포트·DB·시험 계정·렌더 출력은 충돌할 수 있다.
시험 데이터·포트·출력 경로도 작업별로 분리한다.
Blender 원본은 부품·자산별 파일로 나누고 결합 담당자가 연결한다.

## 6. Orchestrator가 할 일

Orchestrator는 한 번에 수백 개 대화를 직접 기억하는 사람이 아니라,
작업 상태를 기록하고 준비된 일을 실행시키는 조정 책임자다.
raphthon에서는 다음을 지속 실행 관리자로 구현해야 한다.

1. 담당 Lead의 작업 분할을 배정 단위로 등록하고 선행 관계·소유권·후보 그룹을 기록한다.
2. 준비된 작업을 가용 인원과 CPU·메모리·GPU·도구 한도 안에서 최대한 실행한다.
3. 디자인·개발뿐 아니라 조사·통합·QA에도 실행 자원을 배정한다.
4. 완료 결과를 분야별 취합 담당자에게 전달하고 다음 작업을 즉시 시작한다.
5. 정체·오류를 감지하면 담당 Lead의 허용 지침 안에서 접근·작업자를 교체한다. 범위·기준은 바꾸지 않는다.
6. 종료 시점 전에는 새 제작보다 후보 선택·통합·최종 QA의 비중을 높인다.

작업을 끝낼 때마다 인원을 줄이는 것이 아니라 다음 품질 향상 작업을 배정한다.
QA나 통합이 밀리면 새 제작에 쓰던 자원을 검수·통합으로 이동한다.
제작만 수백 명으로 늘리고 검수는 한 명에게 몰아주지 않는다.
모든 Sub는 자기 Lead를 통해 지시·변경 요청을 주고받고, 팀 간 협의는 Lead끼리 한다.
실행 장치가 권한 있는 메시지와 자료 위치를 비동기로 전달하므로 메인 모델이 모든 대화를
직접 중계할 필요는 없다. 공용 자료 열람과 보고 취합은 허용하지만 승인권은 넘기지 않는다.

## 7. 6~12시간 동안 계속 이어가기

한 개 에이전트가 같은 대화 맥락을 12시간 유지해야 한다는 뜻은 아니다.
전체 작업이 이어지도록 상태와 결과를 보존하고 개별 작업자는 교체할 수 있어야 한다.

시작할 때 전체 종료 시점, 최종 통합·검수에 남길 시간, 승인된 목표와 권한을 정한다.
단계는 고정된 시간표보다 진행 상태에 맞춰 겹쳐 운영한다.

- 초반: 목표·컨셉·공통 계약 확정과 동시에 독립 조사·대안 탐색.
- 중반: 대량 제작, 준비된 묶음의 통합·QA·수정, 후보 비교를 동시에 수행.
- 후반: 선택한 결과의 전체 일관성, 회귀·실환경 검증, 남은 위험과 결과 인계.

작업·후보·기준 버전·담당·결과·마지막 진행 시각을 지속 저장한다.
작업을 맡긴 유효 기간과 실행 ID를 관리해 중단된 옛 작업이 새 결과를 덮어쓰지 못하게 한다.
재시작 시 실제 프로세스·파일·외부 수행 결과를 대조하고 중복 실행 없이 재개한다.
정해진 시간이 끝났는데 필수 목표가 미충족이면 완료라고 포장하지 않고 남은 항목을 보고한다.

## 8. “토큰 비용 무관”과 실제 제한은 다르다

토큰 사용량을 비용 절감 이유로 낮추지는 않는다. 사용량 기록은 진전·정체를 파악하는
운영 자료로 남길 수 있지만 자체 비용 상한을 새로 만들어 작업을 끊지 않는다.

계정의 실제 사용량·호출 제한, 지원되는 동시 작업 수, 서버·GPU·저장 공간 한도는 지킨다.
실행 자원이 부족하면 그 안에서 최대한 병렬 작업하고 남은 작업은 대기열에서 이어간다.
이는 비용 절감을 위한 소수 운영이 아니라 실제 자원 제약에 대한 처리다.
제한 우회용 계정 증설이나 승인 없는 유료 자원 구매를 전제로 하지 않는다.

여러 실행 호스트·프로세스가 필요하다면 지원·권한·인증 경계를 검증하고
사용자의 필요한 승인을 받은 뒤 확장한다. 단순히 프로세스를 늘렸다고 계정 제한이 늘지는 않는다.

## 9. 실행 인원은 구분해서 보고한다

| 수치 | 의미 |
| --- | --- |
| 역할 수 | 고정 책임 종류. 현재 10개 |
| 준비 작업 수 | 의존 조건이 충족되어 배정할 수 있는 작업 |
| 현재 동시 실행 수 | 지금 실제로 실행되는 작업자 수 |
| 최대 관측 동시 실행 수 | 이번 가동에서 실제 관측한 최대 동시 수 |
| 누적 실행 수 | 교체·재시도를 포함해 지금까지 실행한 수 |
| 대기 수와 이유 | 자원·선행 결과·권한 등으로 대기하는 작업 |

누적 300명을 실행했다고 300명이 동시에 실행됐다고 보고하지 않는다.
목표 동시 수와 실제 동시 수가 다르면 이유를 밝힌다.
인원수뿐 아니라 통합된 결과·목표 충족·검증 증거·남은 결함을 함께 보고한다.

## 10. 구현 완료를 판정할 시험

- 같은 역할의 여러 작업자가 스토리·화면·기능별로 실제 동시에 작업하는가?
- 같은 과제의 독립 후보를 분리 보관하고 근거를 비교해 선택할 수 있는가?
- 많은 작업자가 같은 컨셉·기술 계약 버전을 지키는가?
- 작업 디렉터리·시험 데이터·Blender 원본·출력 파일이 충돌하지 않는가?
- QA·취합·통합 작업도 제작량에 맞춰 처리되는가?
- 많은 Sub가 동시에 일해도 무단 기준 변경·팀 간 지시·QA 승인권 대행을 막는가?
- 개별 실패나 관리자 재시작 뒤 다른 작업을 보존하고 재개할 수 있는가?
- 6~12시간 가동 시험에서 실제 동시 실행 수·결과·중단 원인을 기록하는가?
- 서비스 제한·권한 문제는 준수하면서 보고하고, 사용자 중지 요청을 처리하는가?
- 종료 시점에 완료와 미완료를 증거로 구분해 전달하는가?

문서 보완은 이 시험을 수행한 것이 아니다. 현재 설치에서 수백 개가 가능한지,
어떤 raphthon 실행 관리 구현이 필요한지는 실제 구현 단계에서 확인한다.
