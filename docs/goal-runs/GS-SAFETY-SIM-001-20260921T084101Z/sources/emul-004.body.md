## . RAG 적용 목적

작업자의 현재 위험 상황과 개인 프로필을 바탕으로 현장별 대응 지침을 검색하고, 필요한 내용을 선호 언어와 이해하기 쉬운 표현으로 전달한다.

| 구분 | RAG가 검색할 자료 | 제공할 내용 |
| --- | --- | --- |
| 시뮬레이션 1: 중장비 | 장비별 접근 제한, 작업자 회피 절차, 지원 요청 절차 | 위험 이유, 승인된 회피 행동, 도움 요청 방법 |
| 시뮬레이션 2: 화재·가스 | 현장 비상계획, 물질별 대응 지침, 대피·실내 대기 조건 | 상황에 적용되는 행동 지침과 주의사항 |

위험 감지·경로 계산·통행 가능 여부는 기존 엔진이 담당한다. RAG는 해당 판단에 적용되는 근거를 검색하고 안내 설명을 구성한다.

## 2. 추가 기술 스택

| 항목 | 구현 방식 |
| --- | --- |
| RAG 처리 | 서버 측 TypeScript 모듈 |
| 지식 문서 관리 | Markdown·JSON 기반 승인된 대응 지침 |
| 문서·메타데이터 저장 | 기존 SQLite·Drizzle ORM |
| 키워드 검색 | SQLite FTS5 |
| 의미 검색 | 다국어 임베딩 모델 |
| 벡터 저장 | MVP는 SQLite에 벡터와 모델 버전 저장 |
| 벡터 유사도 계산 | 소규모 문서 대상으로 서버 메모리에서 계산 |
| 검색 결합 | 메타데이터 필터 + 키워드 검색 + 벡터 검색 |
| 안내 설명 생성 | 서버에서 호출하는 LLM |
| 출력 형식 검증 | Zod |
| 기본 안내 | 기존 행동 코드 기반 다국어 메시지 카탈로그 |
| 생성·검색 기록 | SQLite |

SQLite FTS5는 전문 검색 기능을 제공하므로 기존 DB 구성을 유지하면서 키워드 검색을 추가할 수 있다. 임베딩 검색은 별도 구현한다. [SQLite FTS5 공식 문서](https://www.sqlite.org/fts5.html)

LLM과 임베딩 모델은 교체 가능한 인터페이스로 구성하고, 모델명·버전·임베딩 차원은 설정으로 관리한다.

## 3. 개인화 입력 정보

개인 프로필은 구조화된 DB에서 조회한다. 개인 정보를 문서와 함께 무조건 임베딩하지 않는다.

| 정보 | 활용 |
| --- | --- |
| 선호 언어 | 검색된 안내의 표시 언어 선택 |
| 이동 제약 | 적용 가능한 절차 검색, 경로 엔진의 제약 조건 |
| 보조·동행 필요 여부 | 지원 요청 절차 선택 |
| 작업 역할 | 작업자·운전자·대응 담당자별 지침 구분 |
| 현재 위치·위험 구역 | 해당 현장의 구역별 지침 검색 |
| 현재 안내 상태 | 경로 제공·경로 없음·위치 불명에 맞는 지침 선택 |

- 언어는 국적 대신 본인이 선택한 값을 사용한다.
- 나이·성별만으로 이동 능력이나 행동 제약을 추론하지 않는다.
- LLM에는 안내에 필요한 최소 정보만 전달한다.
- 이름·생년월일·의료 진단명 대신 작업자 식별자와 확인된 기능 제약을 사용한다.

## 4. RAG 지식베이스

### 등록할 문서

중장비 시뮬레이션

- 장비별 위험 영역 설명
- 접근 경보 발생 시 행동 절차
- 지정 회피 지점 이용 조건
- 회피 경로가 없을 때의 지원 요청 절차
- 위치 수신 단절 시 안내 절차

화재·가스 시뮬레이션

- 현장별 비상 대응 계획
- 구역별 대피 및 집결 절차
- 물질별 대응 지침
- 대피·지정 공간 이동·실내 대기의 적용 조건
- 이동 지원이 필요한 사람에 대한 절차

```
type KnowledgeDocument = {

  title: string;
  siteId: string;
  simulationType: "equipment" | "fire-gas";
  hazardTypes: string[];
  applicableRoles: string[];
```

문서는 적용 조건·행동·예외가 함께 유지되도록 절차 단위로 분할한다. 예를 들어 “대기하라”는 문장만 분리해 적용 조건을 잃지 않도록 한다.

데모용으로 작성한 문서는 `demo` 자료임을 표시하고 실제 현장 지침과 분리한다.

## 5. 처리 흐름

```
실제 센서 또는 Mock 이벤트
          ↓
위험 엔진: 위험 유형·영향 구역·대상 작업자 판단
          ↓
경로·정책 엔진: 개인 제약을 반영한 경로와 행동 코드 결정
          ├─ 기본 경보·검토된 언어 문구 즉시 전달
          ↓
RAG: 현재 상황에 적용되는 승인 지침 검색
          ↓
LLM: 검색 근거에 한정한 개인별 보조 설명 생성
          ↓
출처·행동 코드·경로 버전·출력 형식 검증
          ↓
검증된 설명을 추가 전달
```

RAG 응답을 기다리느라 기본 경보나 경로 전달이 늦어지지 않도록 한다.

즉시 행동을 요구하는 문구는 검토된 메시지 카탈로그를 사용하고, LLM은 위험 이유와 절차 설명을 보완한다.

## 6. 검색 구현 기준

검색은 다음 순서로 수행한다.

1. 승인 상태와 문서 유효기간을 확인한다.
2. 현장·시뮬레이션 종류·위험 유형·역할로 문서를 제한한다.
3. 필요한 경우 구역·가스 물질 식별자·행동 코드로 추가 제한한다.
4. 필터를 통과한 문서에서 키워드·벡터 검색을 수행한다.
5. 적용 조건과 예외를 확인해 근거를 선택한다.
6. 적합한 근거가 없거나 문서가 충돌하면 생성 대신 기본 안내를 사용한다.

검색 점수는 문서의 유사도를 뜻하며 안전성이나 정답 확률로 표시하지 않는다.

검색된 문서에 포함된 명령은 시스템 지시로 실행하지 않는다. 문서 승인, 접근 범위 필터링, 출처 추적과 출력 검증을 함께 적용한다. [OWASP RAG 보안 지침](https://cheatsheetseries.owasp.org/cheatsheets/RAG_Security_Cheat_Sheet.html)

## 7. 안내 출력 계약

```
type PersonalizedGuidance = {
  guidanceId: string;
  runId: string;
  workerId: string;

  hazardIds: string[];
  actionCode: string;
  routeVersion?: number;
  profileVersion: number;

  locale: string;
  primaryMessageKey: string;
  supplementalExplanation?: string;

  evidence: {
    documentId: string;
    documentVersion: string;
    chunkId: string;
  }[];

  mode: "template" | "rag-assisted";
  generatedAt: string;
  expiresAt: string;
};
```

- `actionCode`와 `routeVersion`은 기존 엔진이 결정한다.
- LLM이 임의의 목적지·좌표·통로·가스 임계값을 추가하지 못하도록 한다.
- 문서 ID와 인용 내용이 실제 검색 결과에 존재하는지 확인한다.
- Zod는 형식 검증에 사용한다. 행동 의미의 일치 여부는 별도 검사한다.
- 생성 중 위험·경로·프로필이 바뀌면 이전 결과를 폐기한다.

## 8. 다국어 안내

- 기본 행동 문구는 한국어·영어의 검토된 번역을 사용한다.
- RAG 보조 설명은 선호 언어로 생성하되 검색 근거의 의미를 유지한다.
- 장비·통로·구역 ID와 숫자·단위는 변경하지 않는다.
- 금지·허용·이동·대기의 의미가 기본 행동 코드와 일치해야 한다.
- 검증되지 않은 번역은 긴급 행동 문구로 사용하지 않는다.
- 미지원 언어는 지원 여부를 명확히 표시하고 등록된 대체 언어와 공통 표지를 제공한다.

```
server/
├─ risk/
├─ routing/
├─ guidance/
│  ├─ policy.ts
│  ├─ templates.ts
│  └─ localization.ts
├─ rag/
│  ├─ ingestion.ts
```

DB에는 다음 테이블을 추가한다.

- `knowledge_documents`: 문서·승인·버전·유효기간
- `knowledge_chunks`: 검색 단위와 적용 조건
- `knowledge_embeddings`: 벡터·임베딩 모델·차원
- `guidance_evidence`: 안내에 사용한 근거
- `rag_runs`: 검색·생성 시간, 모델 버전, 검증 결과, 대체 처리 사유

문서가 수정·폐기되면 관련 검색 인덱스와 캐시를 갱신한다.

| 생성 중 경로 변경 | 이전 결과 폐기 후 최신 상태로 재요청 |
| 개인 프로필 미확인 | 확인된 정보만 사용하고 미확인 상태 표시 |

## 11. 시뮬레이션 검증 항목

시뮬레이션 1

공통

- 문서 출처와 버전을 추적할 수 있는가
- 근거 없음·모델 실패 시 기본 안내가 동작하는가
- 나이·성별만 바꿨을 때 이동 능력을 다르게 추정하지 않는가
- Mock 센서 환경에서도 실제 문서 검색 과정을 실행하는가

## 1. 생성할 지식 문서

| 분류 | 작성할 문서 |
| --- | --- |
| 공통 | 현장·구역 설명, 개인 프로필 적용 원칙, 다국어 안내 기준 |
| 중장비 | 접근 경보, 방향 변경, 회피 경로 변경, 경로 없음, 위치 수신 중단 |
| 화재 | 가상 화재 감지, 통로 차단, 대피 경로 변경, 지정 지점 도착 |

## 2. 가상 환경의 공통 설정

문서마다 다른 장소나 식별자를 만들지 않도록 아래 설정을 고정합니다.

| 항목 | 가상 설정 |
| --- | --- |
| 건설현장 | `SITE-CONSTRUCTION-01` |
| 산업시설 | `SITE-INDUSTRIAL-01` |
| 중장비 | `EQUIPMENT-A` |
| 작업자 | `WORKER-A`, `WORKER-B`, `WORKER-C` |
| 통로 | `PATH-A`, `PATH-B`, `PATH-C` |
| 구역 | `ZONE-A`, `ZONE-B`, `ZONE-C` |
| 지정 회피 지점 | `REFUGE-01`, `REFUGE-02` |
| 집결지 | `ASSEMBLY-01` |
| 가상 대기 공간 | `SHELTER-01` |
| 가스 식별자 | `DEMO-GAS-X` |
| 지원 언어 | 한국어 `ko`, 영어 `en` |

`DEMO-GAS-X`는 실제 물질과 연결하지 않습니다. 실제 가스의 농도 기준·보호구·응급처치 방법을 임의 생성하지 않습니다.

## 3. LLM에 전달할 생성 프롬프트

```
당신은 산업 안전 시뮬레이터의 RAG 테스트용 가상 지식 문서를
작성하는 담당자입니다.

목표는 실제 현장 안전 매뉴얼을 만드는 것이 아니라,
두 개의 독립적인 시뮬레이션에서 문서 검색, 조건 매칭,
개인별 안내, 출처 추적을 검증할 합성 데이터를 만드는 것입니다.

[1. 시뮬레이션 구분]

시뮬레이션 1: equipment
- 중장비와 작업자의 위치·속도·이동 방향을 바탕으로 위험을 판단한다.
- 위험 엔진과 경로 엔진이 위험 대상자, 행동 코드,
  회피 경로 및 목적지를 결정한다.
- RAG 문서는 위험 이유, 적용 조건, 승인된 행동 코드의 설명,
  지원 요청 절차를 제공한다.
- 화재·가스 위험을 이 시뮬레이션에 섞지 않는다.

시뮬레이션 2: fire-gas
- 화재와 가스 mock 이벤트 및 작업자 위치를 사용한다.
- 시나리오 정책이 이동, 지정 공간 이동, 실내 대기 중
  적용할 행동을 결정한다.
- RAG 문서가 임의로 행동 정책을 선택하거나 변경하지 않는다.
- 중장비 이동 위험을 이 시뮬레이션에 섞지 않는다.

[2. 가상 환경]

siteId:
- SITE-CONSTRUCTION-01
- SITE-INDUSTRIAL-01

공통 식별자:
- 장비: EQUIPMENT-A
- 작업자: WORKER-A, WORKER-B, WORKER-C
- 구역: ZONE-A, ZONE-B, ZONE-C
- 통로: PATH-A, PATH-B, PATH-C
- 회피 지점: REFUGE-01, REFUGE-02
- 집결지: ASSEMBLY-01
- 가상 대기 공간: SHELTER-01
- 가스: DEMO-GAS-X

이 식별자의 물리적 연결 관계나 현재 안전 여부를 임의로 만들지 않는다.
실제 이동 경로와 이용 가능한 목적지는 경로 엔진의 입력으로 받는다.

[3. 작성할 문서]

공통 문서:
COMMON-001 개인 프로필 적용 원칙
COMMON-002 선호 언어와 안내 이해 확인
COMMON-003 이동 보조 및 지원 요청
COMMON-004 안내 버전 변경과 오래된 안내 처리

중장비 문서:
EQ-001 중장비 접근 경보
EQ-002 중장비 방향 변경에 따른 안내 갱신
EQ-003 개인 이동 제약을 반영한 회피 안내
EQ-004 유효한 회피 경로 없음
EQ-005 위치 수신 중단
EQ-006 지정 회피 지점 도착 확인

화재·가스 문서:
FG-001 가상 화재 감지와 통로 제한
FG-002 화재로 인한 기존 이동 경로 변경
FG-003 가상 가스 경보와 영향 구역 안내
FG-004 시나리오 정책이 이동을 지정한 경우
FG-005 시나리오 정책이 실내 대기를 지정한 경우
FG-006 화재·가스 복합 위험으로 경로가 없는 경우
FG-007 환경 센서 수신 중단
FG-008 위험 해제와 별도 통행 재개 확인

총 18개 문서를 작성한다.

[4. 개인화 기준]

- 언어는 preferredLocale을 사용한다.
- 국적으로 언어를 추정하지 않는다.
- stairsAllowed, assistanceRequired 등 확인된 제약만 사용한다.
- 나이·성별만으로 이동 속도, 근력, 이해 능력을 추정하지 않는다.
- 프로필 미입력을 '제약 없음'으로 해석하지 않는다.
- 이동 제약에 맞는 경로 선택은 경로 엔진이 담당한다.
- 문서는 해당 제약과 안내가 연결되는 이유를 설명한다.

[5. 허용 행동 코드]

- ALERT_HAZARD
- FOLLOW_VALIDATED_ROUTE
- GUIDANCE_UPDATED
- ROUTE_UNAVAILABLE
- POSITION_UNKNOWN
- SENSOR_UNKNOWN
- REQUEST_ASSISTANCE
- SHELTER_PER_SCENARIO
- CONFIRM_UNDERSTANDING
- CONFIRM_ARRIVAL
- AWAIT_REOPEN_AUTHORIZATION

각 문서는 이 목록에서만 행동 코드를 사용한다.
새로운 행동 코드가 필요해 보여도 추가하지 말고
별도의 작성 메모에 제안한다.

[6. 문서 작성 규칙]

- 모든 문서에 synthetic: true를 표시한다.
- approvalStatus는 draft로 작성한다.
- 실제 승인자, 인증, 법규 준수 사실을 꾸며내지 않는다.
- 실제 현장 사용이 불가능한 시뮬레이션 전용 자료임을 표시한다.
- 문서별로 적용 조건과 적용 제외 조건을 명확히 구분한다.
- 적용 조건, 행동, 예외를 하나의 검색 단위에서 확인할 수 있게 한다.
- '항상 안전하다', '최적의 안전을 보장한다' 같은 표현을 쓰지 않는다.
- 경로, 목적지, 장비 제어, 센서 임계값을 임의 생성하지 않는다.
- 실제 가스 농도 기준, 보호구 선정, 구조·응급처치 절차를 만들지 않는다.
- DEMO-GAS-X를 실제 물질과 연결하지 않는다.
- 실내 대기는 scenarioPolicy가 명시적으로 선택한 경우에만 설명한다.
- 경로가 없다는 이유로 현재 위치에서 대기하라고 일률적으로 지시하지 않는다.
- 위험 해제가 곧 통행 재개를 뜻한다고 작성하지 않는다.
- 수신 확인, 이해 확인, 지원 수락, 도착 확인을 구분한다.
- 원문이나 외부 기관의 실제 지침이라고 주장하지 않는다.

[7. 문서 형식]

각 문서를 Markdown으로 작성하고 다음 YAML 메타데이터를 붙인다.

---
documentId:
title:
siteIds: []
simulationType: common | equipment | fire-gas
hazardTypes: []
applicableRoles: [worker]
profileConditions: {}
actionCodes: []
language: ko
version: 0.1.0
synthetic: true
approvalStatus: draft
sourceReference: synthetic://safety-simulator/
---

본문에는 다음 항목을 순서대로 포함한다.

1. 목적
2. 적용 조건
3. 적용 제외 조건
4. 필요한 입력 필드
5. 행동 코드와 설명
6. 개인화 적용
7. 예외 및 기본 안내
8. 한국어 안내 예시
9. 영어 안내 예시
10. 확인할 상태
11. 검색 키워드
12. 관련 문서 ID

안내 예시에는 실제 경로 대신 다음과 같은 자리표시자를 사용한다.
- {equipmentId}
- {zoneId}
- {nextWaypointLabel}
- {destinationLabel}
- {guidanceVersion}

한국어와 영어의 행동 의미, 금지 표현, 식별자,
자리표시자가 일치하도록 작성한다.

[8. 검색 검증 데이터]

문서 작성 후 rag-test-cases.json을 작성한다.
최소 12개 테스트를 포함한다.

각 테스트 필드:
- testId
- simulationType
- context
- query
- expectedDocumentIds
- forbiddenDocumentIds
- expectedActionCodes
- expectedOutcome: matched | no_match | conflict
- reason

반드시 포함할 테스트:
- 중장비 접근
- 중장비 방향 변경
- 계단 이용 불가
- 영어 안내
- 위치 수신 중단
- 화재로 경로 변경
- DEMO-GAS-X 경보
- 실내 대기 정책이 있는 경우
- 실내 대기 정책이 없는 경우
- 다른 현장 문서 제외
- 관련 지침이 없는 경우
- 서로 충돌하는 지침이 검색된 경우

충돌 문서는 일반 지식 문서에 섞지 않는다.
별도의 negative-fixtures 디렉터리에 테스트 전용으로 작성한다.

[9. 출력 순서]

1. README.md: 사용 범위와 문서 목록
2. knowledge/common/ 아래 공통 문서
3. knowledge/equipment/ 아래 중장비 문서
4. knowledge/fire-gas/ 아래 화재·가스 문서
5. tests/rag-test-cases.json
6. tests/negative-fixtures/ 아래 부정 테스트 자료
7. consistency-report.md: 식별자·행동 코드·번역·관련 문서 검토 결과

실제로 검증하지 않은 항목을 검증 완료라고 쓰지 않는다.
불명확한 조건은 추측으로 채우지 말고 '설정 필요'로 표시한다.
```

## 4. 생성된 문서의 등록 절차

LLM이 작성한 결과는 다음 순서로 RAG에 넣습니다.

1. 생성: 위 프롬프트로 가상 문서 작성
2. 형식 검사: 필수 메타데이터·행동 코드·식별자 검사
3. 내용 검토: 적용 조건, 예외, 한국어·영어 의미 확인
4. 데모 승인: 검토한 문서만 `approved_for_demo`로 변경
5. 색인: 승인된 데모 문서만 분할·임베딩
6. 검색 테스트: 예상 문서와 제외 문서 비교
7. 시뮬레이션 연결: 작업자 프로필과 위험 상태를 검색 조건으로 전달

`approved_for_demo`는 실제 현장 사용 승인이 아닙니다. 운영용 지식베이스와 별도 저장소 또는 명확히 분리된 검색 범위에서 관리합니다.

이 구성으로 먼저 가상 상황 → 관련 지침 검색 → 개인별 언어·조건에 맞는 설명 → 근거 문서 표시까지 검증할 수 있습니다.
