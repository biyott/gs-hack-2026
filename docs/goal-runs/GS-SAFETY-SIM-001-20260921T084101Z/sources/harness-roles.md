# 역할 설명 — 누가 무엇을 책임지나

[전체 구조](./README.md) · [일하는 방법](./harness.md) · [R&R 및 소통 규칙](./responsibilities.md)

역할 이름은 전체 구조 문서의 10개 이름으로 통일한다. “고정”은 담당 책임이
정해져 있다는 뜻이며, 프로그램이 항상 실행되거나 같은 기억을 영구 보존한다는 뜻이 아니다.
같은 역할의 작업자는 대량 복제해 동시에 실행할 수 있다. 역할의 종류와 인원수는 다르다.
이 문서의 업무 분할은 [raphthon 대규모 병렬 운영](./operating-mode.md)을 전제로 한다.

모든 Sub는 받은 업무의 수행·자체 점검·문제 보고를 맡는다. 확정된 기준의 변경과
다른 팀 지휘, 결과의 최종 승인은 맡지 않는다. Lead의 사전 점검·후보 추천도 QA 판정이 아니다.
팀 간 요청은 Lead끼리 전달하고 각 Lead가 자기 Sub에게 지시한다. 실행 배정은 Orchestrator가 관리한다.

## 1. 목표와 실행을 나누는 두 역할

| 역할 | 맡는 일 | 남겨야 할 결과 | 맡지 않는 일 |
| --- | --- | --- | --- |
| 총괄 PM | 요구 파악, 범위·우선순위 정리, 사용자 결정 요청, 최종 보고 | 목표·제외 범위·결정 기록·완료 보고 | 팀원 생성과 재시도 관리, QA 실패를 통과로 변경 |
| Orchestrator | 작업자 배정, 순서·동시 작업 수 관리, 결과 수집, 실패 처리 | 작업 목록·담당자·진행 기록·차단 사유 | 목표·기획·디자인·기술 계약 변경, QA 대신 합격 판정 |

예: “이번에는 모바일 앱을 제외하자”는 총괄 PM이 사용자와 확인할 사안이다.
“모바일 작업을 빼고 준비된 웹 기능들을 다수 작업자에게 병렬 배정하자”는 Orchestrator의 실행 사안이다.

## 2. 리서치팀

**리서치 Lead(Research Lead)**는 정보 조사 책임자다.
무엇을 알아야 하는지 질문으로 나누고, 출처의 품질과 자료의 빈틈을 확인하고,
기획·디자인·개발·QA가 사용할 수 있게 결과를 정리한다.
서브 리서처(Researcher)는 분야별 탐색 담당자다.

| 서브 리서처 | 찾는 것 | 전달할 내용 |
| --- | --- | --- |
| 대상·배경 리서처 | 정확한 제품·기종·용어, 관련 사례와 배경 | 식별 근거, 후보 비교, 다른 대상과 구분할 특징 |
| 기술·제원 리서처 | 공식 제품 문서, 치수·구성·기술 제약 | 출처가 붙은 제원표, 적용 모델·구성·단위 |
| 시각 자료 리서처 | 여러 각도의 사진·영상·도면, 부품별 외관 | 원본 출처, 시점·부품 설명, 보이지 않는 부분, 이용 조건 |
| 출처 검증 리서처 | 주장과 원문 일치, 서로 다른 자료의 충돌 | 확인·추정·미확인 구분, 충돌 원인과 추가 질문 |

네 종류는 작업을 나누는 기준이지 네 명으로 제한한다는 뜻이 아니다.
같은 종류의 리서처도 주제·언어·출처군·가설별로 여러 명을 동시에 실행한다.
독립 교차검증을 위해 같은 질문을 복수 리서처에게 맡길 수도 있다.
Lead가 조사를 설계하고 Orchestrator가 실제 가용 한도 안에서 최대한 병렬 배정한다.

리서치팀은 찾은 정보를 바탕으로 추천할 수 있지만 제품 목표·디자인·기술 결정을
대신하지 않는다. 이미지 생성이나 Blender 제작도 디자인팀의 일이다.
출처 검증 리서처는 자료의 신뢰성을 확인하고, QA Lead는 최종 결과의 목표 달성을 판정한다.
조사 보고서 자체가 납품 대상이면 QA가 요청 범위와 핵심 근거를 독립적으로 확인한다.

최종 결과는 [조사 자료 묶음](./research.md)으로 전달한다.
원문을 읽지 못했거나 치수를 찾지 못했다면 그 사실을 적고 빈칸을 상상으로 채우지 않는다.

## 3. 기획팀

**기획 Lead**는 기능·흐름·정책·예외를 구체적으로 정리하고 모순을 해결한다.
총괄 PM이 정한 목표를 자세히 풀되, 새 기능을 마음대로 추가하지 않는다.

서브 기획자는 필요에 따라 요구사항 분석, 사용자 흐름, 정책·예외로 나눈다.
외부 사실 조사는 기획 Lead를 통해 리서치 Lead에 요청하고, 받은 근거를 실제 기능과 정책으로 구체화한다.
각자 맡은 부분을 제출하고 기획 Lead가 하나의 명세로 모은다.
여러 기획자가 서로 다른 최종안을 각각 확정하지 않는다.
승인된 기획의 모순을 발견해도 Sub가 정책·범위를 바꾸지 않는다.
기획 Lead가 변경안을 정리하고 권한자의 승인 뒤 새 버전으로 배정한다.

## 4. 디자인팀

**UI 디자이너 Lead**는 웹·모바일 화면과 3D 자산의 디자인 방향을 함께 책임진다.
색상·글자·간격·분위기 등 공통 기준을 정하고, 서브 디자이너에게 일을 나눈다.
기술적으로 구현 가능한 범위는 개발 Lead와, 검수 기준은 QA Lead와 맞춘다.
리서치팀이 넘긴 사진·제원에서 확인된 부분과 추정한 부분을 구분해 사용한다.

| 서브 디자이너 | 만드는 것 | 전달할 내용 |
| --- | --- | --- |
| 웹 디자이너 | 웹 화면, 화면 크기별 배치, 버튼·로딩·오류 상태 | 화면 설계, 공통 스타일 기준, 이미지·아이콘, 상호작용 설명 |
| Blender 디자이너 | 3D 모델, 재질, 조명, 필요 시 애니메이션 | 원본 `.blend`, 필요한 내보내기 파일, 미리보기, 사용·검증 설명 |
| 모바일 UI 디자이너 | 앱 화면, 터치 흐름, 플랫폼별 상태 | 화면·동작 설계, 크기·간격 기준, 전달용 자산 |
| 기타 전문 디자이너 | 필요한 모션·아이콘·일러스트 등 | 요청한 목적에 맞는 원본·결과물·사용 조건 |

모바일 UI와 기타 전문 디자이너는 목표에 해당하는 작업이 있으면 추가한다.
웹·Blender 디자이너는 같은 역할이라도 다수 동시 실행을 기본 확장 방식으로 삼는다.

UI 디자이너 Lead는 먼저 전체 컨셉·공통 스타일·화면 연결 원칙을 정한다.
동결된 기준은 Lead도 변경 절차 없이 덮어쓰지 않는다.
서브 디자이너는 이 기준 아래에서 스토리·화면·상태·화면 크기별로 나누어 작업한다.
한 화면의 대안을 여러 명에게 맡길 때도 공통 기준은 같고 후보 ID와 저장 위치는 다르다.
Blender도 부품·장면·재질별 작업을 분리하고 원본 파일의 결합 담당자를 둔다.
다수의 결과를 한 명이 전부 직접 다듬느라 멈추지 않도록 화면군·자산군별 취합 작업자를
둘 수 있지만 최종 디자인 방향의 책임은 UI 디자이너 Lead에 남긴다.

### 디자인 결과를 개발팀에 전달할 때

팀 간 제작 조건은 UI 디자이너 Lead와 개발 Lead가 협의한다.
실제 자료는 공유 저장소로 전달하고 개발자는 자기 Lead의 업무 카드로 구현한다.
디자이너 Sub가 개발자 Sub에게 직접 변경을 지시하지 않는다.

웹 화면은 정상 화면뿐 아니라 필요한 로딩·빈 화면·오류 상태와 작은 화면의
동작까지 설명한다. 구체적인 크기나 색상은 공통 기준으로 남겨 구현자가 추측하지 않게 한다.

Blender 작업은 제작 전에 다음을 합의한다.

- 결과를 쓸 곳: 웹, 앱, 영상, 이미지, 또는 Blender 원본 자체.
- 단위·크기·방향, 필요한 파일 형식, 재질·텍스처·움직임의 범위.
- 대상 환경에 맞는 파일 용량과 복잡도 기준. 숫자는 프로젝트별로 정한다.
- 외부 텍스처·모델의 출처와 이용 조건.

Blender 디자이너는 원본 열기와 필요한 내보내기를 확인한다.
개발자는 실제 앱에서 자산을 불러와 기능을 연결한다.
UI 디자이너 Lead는 디자인 의도와 사전 점검 의견을 남긴다.
디자인 일치 여부를 포함한 공식 검증과 합격·반려는 최종 환경에서 QA가 수행한다.
사용 가능한 Blender 도구가 없으면 실제 제작·검증 완료라고 보고하지 않는다.

## 5. 개발팀

**개발 Lead**는 전체 기술 구조, 화면과 서버의 연결 방법, 데이터 구조,
디자인·3D 자산의 연결 방식과 최종 통합을 책임진다.
모든 질문을 중계하는 역할이 아니라 여러 분야가 합의해야 할 기술 결정을 맡는다.

| 분야 책임자 | 작업자 | 책임 |
| --- | --- | --- |
| Frontend Lead | Frontend 개발자들 | 웹 화면·사용자 조작·서버 연결·웹에서의 3D 표시 |
| Backend Lead | Backend 개발자들 | 서버 기능·데이터·인증·API |
| Mobile Lead | Mobile 개발자들 | 모바일 앱의 화면·기능·기기 연결 |

분야 책임자는 작업을 파일·기능 단위로 나누고 기술적 사전 점검과 후보 추천을 한다.
이는 QA의 공식 검증·합격 판정을 대체하지 않는다.
같은 FE 역할도 기획 항목·사용자 스토리·기능·화면별로 수백 개 작업자를 배정할 수 있는
규모를 목표로 한다. 실제 동시 수는 실행 환경에서 확인한다.
공통 API·상태·컴포넌트 규칙을 먼저 공유하고, 작업별 수정 영역과 격리 공간을 지정한다.
공통 라이브러리 변경과 여러 후보의 통합은 별도 담당 작업으로 분리한다.
개발자는 맡은 구현과 자체 테스트를 수행한다. 서버 계약·공통 스타일·공유 자산을
바꿔야 하면 자기 Lead에게 변경 요청을 제출한다. Lead 간 협의와 필요한 승인이 끝나기
전에는 기존 계약을 바꾸지 않는다. 디자인 변경을 단순 구현 편의로 결정하지 않는다.

## 6. QA팀

**QA Lead**는 처음부터 합격 기준을 만들고 마지막에 목표 달성 여부를 판정한다.
기획 누락과 검증 불가능한 조건을 먼저 찾아내며, 개발팀이나 디자인팀 아래에 속하지 않는다.

| 서브 QA | 검사하는 것 | 남길 증거 |
| --- | --- | --- |
| 목표 QA | 사용자의 필수 요구가 빠짐없이 달성됐는지 | 목표별 결과와 누락 목록 |
| 기능 QA | 기능·연결·오류 처리가 실제로 동작하는지 | 실행 절차와 관찰 결과 |
| 디자인 QA | 승인된 디자인, 화면 크기별 동작, 접근성 | 비교 화면·조작 기록·차이점 |
| 3D QA | 모델·재질·움직임·파일 전달이 목적에 맞는지 | 원본 열기, 내보내기·불러오기, 최종 사용 환경의 결과 |
| 회귀 QA | 기존 동작과 코드 품질을 해치지 않았는지 | 테스트·검사 결과와 구체적인 문제 위치 |
| 보안 QA | 권한·민감정보·데이터 보호를 지키는지 | 권한 거부·데이터 상태 검사 |
| 성능·복구 QA | 합의한 부하에서 작동하고 장애 후 복구되는지 | 조건을 명시한 측정·복구 기록 |

목표에 맞는 QA 분야를 선택하고, 각 분야 안에서 화면·기능·브라우저·기기·위험별로
다수의 서브 QA를 동시에 실행한다. 같은 결과물을 독립적으로 이중 검증할 수도 있다.
대량 제작에 비례해 검수 인원도 늘린다. 결과물을 만든 에이전트가 자기 작업의
공식 QA 검증자나 최종 승인자가 되지는 않는다. 역할 이름만 바꿔도 동일한 제한을 적용한다.
서브 QA는 배정 항목의 판정과 증거를 제출하며, QA Lead만 통합 후보의 공식 판정과
인수 승인을 발행한다. PM·Orchestrator·분야 Lead는 이를 덮어쓸 수 없다.
QA는 실패한 제품을 직접 수정하거나 목표·기준을 몰래 완화하지 않는다.
디자이너의 자체 점검과 QA의 독립 검증을 서로 대체하지 않는다.

## 7. 의견이 충돌하면

| 상황 | 처리 |
| --- | --- |
| 출처마다 기종·치수·구성이 다름 | 리서치 Lead가 적용 대상과 원문을 확인. 해결 안 된 내용은 미확인으로 전달 |
| 디자인이 기술·성능 조건과 맞지 않음 | UI 디자이너 Lead와 개발 Lead가 대안 정리. 목표·범위 변경은 총괄 PM이 사용자에게 확인 |
| 개발팀은 완료라고 하지만 QA는 실패 | QA Lead가 근거를 담당 Lead로 전달. Orchestrator가 승인된 수정 작업 배정. QA 재검증 전에는 합격 아님 |
| QA 기준 자체가 잘못됨 | QA Lead가 변경 요청·근거·버전·재검증 범위를 기록. 합격 조건·목표 변경이면 해당 기준 소유자와 PM/사용자 승인 필요 |
| 무엇을 만들지 불명확함 | 기획 Lead가 선택지 정리, 총괄 PM이 사용자에게 필요한 결정 요청 |

## 8. 모든 작업자가 받을 업무 카드

담당 책임자가 다음을 적고 Orchestrator가 실행을 배정한다.

1. 무엇을 만들거나 확인할지.
2. 참고할 목표·기획·디자인·기술 자료와 버전.
3. 수정해도 되는 파일과 다른 작업자가 맡은 영역.
4. 사용할 환경·도구, 허용된 작업과 금지된 작업.
5. 제출할 결과물과 합격 기준.
6. 6~12시간 전체 일정 중 이 작업의 시간 범위, 진행 정체 시 전환 기준과 보고할 내용.
7. 같은 역할의 다른 작업자와 구분하는 작업 ID, 비교 후보 ID, 기준 버전과 취합 담당자.
8. 자기 Lead, 스스로 결정해도 되는 부분, 바꿀 수 없는 결정, 변경 요청·소통·위험 신고 경로.

결과 제출에는 만든 것, 실제 검사한 것, 증거 위치, 못 한 것을 구분한다.
다른 작업자의 변경을 지우지 않으며, 같은 파일을 건드려야 하면 자기 Lead에게 요청한다.
