# Codex QA 및 실행 하네스

[팀 구성](./README.md) · [역할 계약](./roles.md) · [R&R 및 소통 규칙](./responsibilities.md) · [근거](./references.md)

상태 이름과 아래 정책은 프로젝트의 설계다. Codex 내장 상태나 설정 키가 아니며,
메인 세션의 도구 제공만으로 지속 실행·권한 강제·자동 복구가 구현되는 것은 아니다.
실행·변경·판정 권한은 R&R 문서를, 실행 규모·시간·토큰 정책은
[대규모 병렬 운영](./operating-mode.md)을 기준으로 한다.

## 1. 제어와 실행 분리


| 영역    | 책임                                     |
| ----- | -------------------------------------- |
| 목표    | 총괄 PM이 목표·비목표·승인 범위를 유지                |
| 작업 배정 | 메인 Orchestrator가 작업자 생성·대기·후속 요청·중단 관리 |
| 기술 통합 | 개발 Lead가 승인된 기준 버전과 인터페이스에 따라 통합     |
| 검증    | QA팀이 공식 검증을 수행하고 QA Lead만 종합 판정·인수 승인 발행 |
| 상태 보존 | 작업 원장과 실행 증거를 세션 밖에 기록                 |
| 권한·한도 | 실행 환경과 도구 경계에서 강제; 프롬프트만으로 보장하지 않음     |


현재 도구 표면의 에이전트 ID는 호출 결과를 사용하며 임의로 만들지 않는다.
대기는 제공되는 대기 기능을 사용하고 상태를 짧은 간격으로 반복 조회하지 않는다.
중단 요청 후에는 실제 중단 여부와 이미 수행된 변경을 확인한다.
메인은 작업 결과를 받기 전에 완료라고 보고하지 않는다.
Sub는 자기 Lead에게 보고하고 팀 간 지시·변경 협의는 Lead끼리 진행한다.
Orchestrator는 승인된 업무를 전달할 뿐 기획·기술 결정이나 QA 승인을 대신하지 않는다.

## 2. 목표 계약

각 목표는 ID, 원 요청, 명세 버전, 비목표, 필수 여부, 관찰 가능한 인수 기준,
검증 방법, 담당 QA, 관련 작업·증거를 가진다.
기획이 상세화하고 PM이 범위를 관리하며 QA가 검증 가능성을 확인한다.

예를 들어 회원가입은 버튼 존재가 아니라 계정 생성·로그인 성공과 중복 가입 거부 등
승인된 사용자 결과를 기준으로 한다. 명세 변경은 담당 Lead의 변경 요청과 해당 권한자의
승인을 먼저 기록한 뒤 버전을 올리고 영향 검증을 다시 한다. Sub가 원본을 고칠 수 없다.
기준을 정하는 승인, QA가 결과를 인수하는 승인, 사용자가 외부 작업을 허가하는 승인을 구분한다.

## 3. 실행 게이트


| 단계       | 단계 산출물·조건                  | 책임                    |
| -------- | -------------------------- | --------------------- |
| G0 목표 준비 | 승인된 목표·범위, 동결된 인수 기준·검증 방법 | PM·담당 Lead는 기준 정리, QA Lead는 검증 계획 |
| G1 실행 준비 | 계약·의존성·파일 소유권·작업 경로·실제 한도 확인 | 개발 Lead + 메인 |
| G2 구현 제출 | 구현 결과와 자체 테스트 증거 제출. 합격 판정 아님 | Sub 제출, 분야 Lead가 제출 준비·후보 추천 |
| G3 통합 준비 | 통합 후보와 실행 환경 고정. 합격 판정 아님 | 개발 Lead |
| G4 목표 검증 | QA가 필수 기준 검증. QA Lead가 공식 합격·반려·보류 발행 | QA Lead |
| G5 결과 보고 | QA가 승인한 범위와 미충족·위험·필요 승인을 구분해 공개 | PM이 보고 정리, 메인이 전달. 별도 품질 승인 아님 |


작은 변경은 중간 기록을 간소화하되 필수 인수 기준을 생략하지 않는다.
G0~G3는 업무 준비와 제출 단계이지 분야 Lead가 결과를 승인하는 단계가 아니다.
공식 결과 승인 단계는 G4뿐이다. G5는 실패·미완료도 그대로 보고하며 QA 판정을 변경하지 않는다.
QA 통과는 commit·push·배포·메시지 발송의 자동 허가가 아니다.
그 작업에 대한 사용자 요청과 적용되는 승인 정책을 별도로 확인한다.

## 4. 상태와 완료 판정

```text
DRAFT → READY → RUNNING → INTEGRATING → VERIFYING → ACCEPTED → DONE
                   ↑                       │
                   └──── REWORK ←──────────┘
```

진행 중 외부 조건 부족은 BLOCKED, 사용자 중지는 PAUSED, 예산 소진은
BUDGET\_EXHAUSTED, 종결 실패는 FAILED, 취소는 CANCELLED로 기록한다.
이것은 작업 원장의 상태이며 Codex 도구의 상태 이름과 구분한다.
사용자 요청이 없는 자체 토큰 비용 상한을 만들지는 않는다. 6~12시간 가동 종료나
실제 서비스 한도로 중단되면 미완료 범위와 이유를 남기며 DONE으로 처리하지 않는다.

QA 판정은 PASS / FAIL / BLOCKED / NOT\_RUN으로 구분한다.
증거 누락·미실행·판정 불가를 통과로 바꾸지 않는다.
서브 QA의 항목별 결과와 QA Lead의 통합 후보 종합 판정을 구분한다.
`VERIFYING → ACCEPTED`는 현재 후보·기준·환경에 대한 QA Lead의 유효한 종합 PASS가
있을 때만 허용한다. 실행 관리자는 그 판정을 검증해 기록할 뿐 자기 판단으로 만들 수 없다.
`ACCEPTED → DONE`은 필요한 인계·보고와 별도 승인 조건을 기록하는 단계다.
정상 DONE은 다음을 모두 만족해야 한다.

1. 승인된 목표 버전의 모든 필수 기준이 PASS.
2. 증거가 현재 통합 후보와 관련 환경에 대응.
3. 정책상 완료를 막는 결함이 없음.
4. 필요한 사용자 승인과 인계 자료가 준비됨.

사용자의 위험 수용은 원래 실패와 예외를 남겨 별도 보고한다. 그 자체로 QA PASS나
정상 ACCEPTED/DONE을 생성하지 않는다.
사용자가 목표를 변경하면 새 버전에 대해 재판정한다.
PM이나 메인이 QA의 실패를 덮어쓰지 않는다.

## 5. QA 실행과 증거

서브 QA는 위험에 필요한 분야만 실행한다. QA Lead가 직접 작은 작업을 검증할 수도
있지만 구현자가 자기 결과의 공식 검증자나 최종 승인자가 되지는 않는다.
동일 후보에 대해 역할 이름만 바꾸어 이 제한을 우회할 수 없다.
최종 판정은 서로 다른 개발 브랜치가 아닌 같은 통합 후보에 대해 수행한다.

모든 증거에는 목표·작업·실행 ID, 명세 버전, 커밋 또는 후보 내용 해시, 환경,
시험 데이터 조건, 검증 절차, 기대·관찰 결과, 시각과 산출물 경로를 남긴다.
미커밋 코드라면 커밋 ID만으로 후보를 식별하지 않고 변경 내용도 식별한다.

자동 확인 가능한 조건은 테스트와 실제 상태 확인을 사용한다. 주관적인 품질에는
명시적 평가표와 필요한 사용자 판단을 사용한다. 여러 AI의 동의만으로 검증을 대체하지 않는다.
스크린샷만으로 데이터 저장이나 권한 차단을 증명하지 않는다.

QA 중 코드·명세·환경이 바뀌면 QA가 영향 범위를 확인하고 해당 검증을 다시 한다.
기존 종합 PASS는 새 후보에 적용하지 않는다. 영향 없는 증거의 재사용도 QA가 기록하고
새 종합 판정을 발행한다. QA는 결함을 직접 수정하지 않고 담당 Lead에 전달한다.
검사에 필요한 도구가 없으면 미검증 범위를 공개한다.
비밀정보·개인정보를 증거와 대화에 노출하지 않는다.

## 6. 재작업과 실패 처리


| 원인          | 다음 행동                              |
| ----------- | ---------------------------------- |
| 제품 결함       | QA Sub → QA Lead → 담당 Lead → 메인 배정 → Sub 수정 → QA 재검증 |
| 기술 계약 충돌    | 개발 Lead와 관련 Lead가 변경안 협의. 승인·새 버전 기록 후 영향 작업·검증 재실행 |
| 모호한 명세      | 기획 Lead가 변경안 정리, PM이 위임 범위 안에서 결정하거나 사용자 결정 요청 |
| 환경 장애       | 제품 실패와 구분, 환경 복구 작업으로 배정           |
| 잘못된 평가기     | QA Lead가 근거·변경 버전 기록 후 재평가. 목표·합격 조건 변경은 별도 승인 필요 |
| 인증·권한·한도 부족 | 차단 또는 예산 중지 기록, 필요한 사용자 결정 요청      |


초기 운영안은 자동 재작업 2회, 동일 환경 오류 재시도 1회다.
이는 Codex 기본값이 아니며 요청별로 합의할 정책이다. 한도 후에는 근거와 선택지를
보고한다. 불안정한 테스트를 성공할 때까지 반복하고 이전 실패를 숨기지 않는다.
재시도나 다른 접근을 배정해도 Sub의 수정 범위·승인권이 확대되지 않는다.

## 7. 동시 실행과 파일 소유권

작업 시작 시 현재 도구·설정·계정의 한도를 확인한다. 전체 동시 실행 한도를
부모별 제한과 혼동하지 않으며 개발 작업이 QA 실행 기회를 독점하지 않게 한다.
현재 세션에서 보이는 슬롯 수를 다른 설치의 기본값으로 복사하지 않는다.

읽기 중심 분석은 병렬화하기 쉽지만 쓰기 작업은 독립된 파일 소유권이 필요하다.
공유 디렉터리에서는 다른 작업자의 편집이 즉시 보일 수 있다. 공통 파일 변경은
담당자를 하나로 정한다. 분리된 worktree에서도 포트·DB·테스트 계정 충돌을 확인한다.
타인의 변경을 되돌리거나 사용자 미커밋 작업을 정리 대상으로 취급하지 않는다.

## 8. 지속 기록과 복구

다음은 향후 구현할 논리적 기록이며 실제로 생성한 경로나 내장 Codex 기능이 아니다.


| 기록        | 소유 역할            | 내용                   |
| --------- | ---------------- | -------------------- |
| 목표 계약     | PM               | 원 요청·범위·버전·승인        |
| 기술 계약     | 개발 Lead         | 인터페이스·소유권·통합 기준      |
| 작업 원장     | 메인               | 의존성·실행 ID·담당·상태·한도   |
| QA 추적표·판정 | QA Lead          | 목표별 검사·대상 후보·판정      |
| 실행 증거     | 실행자              | 로그·관찰 결과·재현 절차       |
| 승인·예외     | 사용자 결정 기록        | 외부 작업 승인·범위 변경·위험 수용 |
| 재개 요약     | 메인               | 완료·차단·다음 작업·증거 위치    |

역할·업무 카드·허용 소통 경로와 기준 변경 요청·승인 기록도 보존한다.
QA 판정은 QA 전용 발행 경로로 보호하고 기존 FAIL과 변경 이력을 삭제하지 않는다.


세션을 재개하거나 새 에이전트를 만들 때 기록과 실제 코드·프로세스를 대조한다.
저장된 대화가 있다는 사실은 이전 작업자가 살아 있거나 외부 작업이 미실행이라는
뜻이 아니다. 사용자 작업을 복구 명목으로 초기화하지 않는다.

상시 실행 하네스를 별도 구현한다면 단일 상태 작성자 또는 트랜잭션, 실행 임대와
생존 신호, 오래된 실행의 갱신 거부가 필요하다. 외부 쓰기는 멱등 키나 결과 조회로
중복을 방지하고 결과가 불명확하면 재실행 대신 차단한다.

## 9. 선택형 Discord 어댑터

메시지 → 요청자 확인 → 중복 제거 → 프로젝트·작업 연결 → Codex 실행 → 결과 보고의
경계를 둔다. 외부 메시지가 임의 프로젝트·명령·권한을 지정하도록 허용하지 않는다.
승인은 작업 ID와 승인할 변경에 묶고 다른 요청에 재사용하지 않는다.

어댑터 인증과 Codex의 ChatGPT 로그인은 별개다. Codex 토큰을 Discord에 전달하거나
사용자에게 붙여 넣도록 요구하지 않는다. 원격 실행 인터페이스의 안전성과 지원 상태를
검증하기 전 공개 서비스로 노출하지 않는다.

## 10. 하네스 인수 시험

- 증거 없는 완료 선언, 필수 QA 미실행은 DONE으로 전이되지 않는다.
- QA 도중 후보 변경 시 오래된 PASS 적용이 차단된다.
- 구현자의 판정 기록 변경은 강제 통제 모드에서 거부된다.
- Sub의 확정 명세 변경, 타 팀 지휘, 분야 Lead·PM·Orchestrator의 QA 승인 발행이 거부된다.
- 서브 QA의 부분 PASS만으로 전체 후보가 합격 처리되지 않는다.
- 기준 변경 승인 후 영향 작업만 갱신하고 이전 버전의 종합 PASS를 재사용하지 않는다.
- 일반 전달 경로 장애 중에도 긴급 위험 신고와 자기 작업 중지가 가능하다.
- 중복 요청은 작업과 외부 효과를 중복 생성하지 않는다.
- 작업자 중단·메인 재시작 후 실제 상태를 확인하고 재개한다.
- 여러 Lead의 동시 생성 요청에도 전체 한도와 QA 실행 기회가 유지된다.
- 반복 실패는 정해진 한도에서 중지하고 원인을 보고한다.
- 외부 작업 응답 유실은 결과 조회 또는 차단으로 처리한다.
- CLI·앱의 작업 경로가 다르면 이를 감지하고 잘못된 checkout을 수정하지 않는다.
