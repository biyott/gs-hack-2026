# Codex 팀 — 여기부터 읽으세요

작성일: 2026-09-21 · 정보 조사·기획·디자인·개발·QA를 포함한 팀 설계

## 한 문장으로

**당신이 목표를 말하면, Codex가 필요한 정보를 조사하고 기획·디자인·개발을 나누어 진행하며,
QA가 정말 목표를 달성했는지 확인한 뒤 결과를 보고하는 팀이다.**

당신은 지금처럼 Codex 대화창 하나와 이야기하면 된다.
팀원마다 별도로 설명하거나 작업 상황을 직접 모으러 다닐 필요는 없다.

이 문서는 앞으로 운영할 팀의 설계다. 문서를 작성했다고 팀이 설치되거나
계속 실행되는 것은 아니다. 기존 Hermes 문서는 별도로 유지한다.

## 가장 먼저 정할 R&R

- **Sub:** 맡은 업무 수행·자체 점검·문제 보고. 확정된 기획이나 자기 범위 밖의 결정은 바꾸지 않는다.
- **Lead:** 자기 분야의 기준·작업 분할·변경안·후보 추천. 결과의 최종 합격을 대신 결정하지 않는다.
- **QA:** 공식 결과 검증을 맡고, QA Lead만 합격·반려·판정 보류를 발행한다.
- **Orchestrator:** 승인된 일을 배정·전달·기록한다. 기준이나 QA 판정을 덮어쓰지 않는다.
- **총괄 PM:** 사용자와 목표·범위를 관리하고 QA 판정을 보고한다. QA 실패를 통과로 바꾸지 않는다.

업무 지시와 변경 협의는 **Sub ↔ 자기 Lead**, **팀 사이에는 Lead ↔ Lead**로 전달한다.
이미 승인된 자료는 접근 권한 안에서 직접 읽어도 되지만, 읽기가 지시·변경 권한은 아니다.
기준을 바꾸려면 변경 요청과 승인·새 버전·재검증이 필요하다.
자세한 권한표와 예외는 [R&R 및 소통 규칙](./responsibilities.md)을 기준으로 한다.

## 이 하네스의 가장 중요한 전제

**raphthon에서 구현할 이 하네스는 6~12시간 동안 가능한 최대 규모의 에이전트가
동시에 조사·기획·디자인·개발·검증을 수행해 최상의 결과를 만드는 것을 목표로 한다.**

- 토큰 비용 절감은 운영 목표가 아니다. 품질을 높일 대안 제작·추가 조사·재검증을 적극 수행한다.
- 같은 역할은 한 명으로 제한하지 않는다. 화면·스토리·기능별로 같은 역할의 작업자를 대량 실행한다.
- 같은 문제도 서로 다른 해법을 비교하려면 여러 작업자에게 독립적으로 맡길 수 있다.
- FE 개발자만 수백 명이 동시에 작업하는 규모도 설계 목표에 포함한다.
- 고정 책임자 10개는 조직의 역할 수이지 작업자 수나 동시 실행 수의 상한이 아니다.

여기서 최대 규모는 실제 실행 환경·계정·도구가 허용하는 범위다.
토큰 비용을 신경 쓰지 않는다는 요청이 서비스의 사용량 제한이나 권한을 없애지는 않는다.
수백 개 동시 실행이 현재 Codex 세션에서 검증됐다는 뜻도 아니다.
사용자가 지정한 구현 대상 이름은 그대로 **raphthon**으로 표기하며 기존 제품 기능을 추정하지 않는다.

자세한 운영 전제와 장시간 병렬 작업 방식은 [대규모 병렬 운영](./operating-mode.md)을 기준으로 한다.

## 1. 사람으로 생각하면 쉽다

당신은 최종 결정권자다. Codex 안에는 다음 책임자들이 있다.

| 책임자 | 쉬운 설명 | 책임지는 질문 |
| --- | --- | --- |
| 총괄 PM | 당신의 요구를 정리하는 프로젝트 책임자 | 무엇을, 왜, 어디까지 만들까? |
| Orchestrator | 업무 배정·순서·진행을 관리하는 실행 조정자 | 누구에게 맡기고, 무엇부터 할까? |
| 리서치 Lead | 근거 있는 자료를 모아 전달하는 정보 조사 책임자 | 무엇을 확인했고, 아직 무엇을 모르는가? |
| 기획 Lead | 기능과 사용 흐름을 정리하는 기획 책임자 | 사용자가 어떻게 사용하게 할까? |
| UI 디자이너 Lead | 화면과 3D 디자인을 맞추는 디자인 책임자 | 어떻게 보이고 조작되어야 할까? |
| 개발 Lead | 기술 구조와 전체 연결을 책임지는 개발 총책임자 | 어떻게 구현하고 연결할까? |
| Frontend Lead | 웹 화면 개발 책임자 | 화면을 어떻게 실제로 작동시킬까? |
| Backend Lead | 서버·데이터 개발 책임자 | 데이터와 서버 기능을 어떻게 처리할까? |
| Mobile Lead | 모바일 앱 개발 책임자 | 모바일에서 어떻게 구현할까? |
| QA Lead | 목표와 품질을 독립적으로 검사하는 검수 책임자 | 정말 요청한 결과가 나왔나? |

고정 책임은 총 10개다. 각 Lead 아래의 작업자 수는 역할당 한 명으로 제한하지 않는다.
Lead는 해당 분야의 책임자라는 뜻이다.
이전 문서의 Engineering Lead는 앞으로 **개발 Lead**라고만 부른다.
총괄 PM과 Orchestrator는 다른 역할이며, 하나로 합치지 않는다.

## 2. 전체 팀 모습

아래는 **책임 관계**다. 프로그램이 에이전트를 생성하는 순서는 아니다.

```text
당신 ↔ Codex 대화창
             │
          총괄 PM ── 목표·우선순위·중요 결정
             ↕
       Orchestrator ── 업무 배정·진행·실패 처리
             ├─ 리서치 Lead
             │    └─ 서브 리서처들 — 대상·제원·시각 자료·출처 확인
             ├─ 기획 Lead
             │    └─ 서브 기획자들
             ├─ UI 디자이너 Lead
             │    ├─ 웹 디자이너들
             │    ├─ Blender 디자이너들
             │    └─ 전문 분야별 다수의 디자이너들
             ├─ 개발 Lead
             │    ├─ Frontend Lead → Frontend 개발자들
             │    ├─ Backend Lead  → Backend 개발자들
             │    └─ Mobile Lead   → Mobile 개발자들
             └─ QA Lead
                  └─ 서브 QA들
```

총괄 PM은 목표를 책임지고, Orchestrator는 그 목표에 맞춰 일을 배정한다.
QA Lead는 개발 Lead의 부하가 아니다. 개발팀이 완료했다고 말해도 독립적으로 검사한다.
UI 디자이너 Lead는 이름에 UI가 들어가지만, 이 팀에서는 웹·모바일 화면과
Blender 3D 자산의 디자인 방향까지 묶어 책임진다.

리서치 Lead는 모든 팀이 필요할 때 이용하는 정보 조사 책임자다.
기획팀 아래에만 두지 않는다. 기획·디자인·개발·QA 모두 자기 Lead를 통해 자료를 요청할 수 있다.
일을 시작할 때뿐 아니라 만들다가 모르는 내용이 생겼을 때도 조사한다.

### 리서치팀을 사람으로 비유하면

“디자이너와 개발자가 믿고 쓸 자료를 찾아 정리하는 조사팀”이다.
리서치 Lead가 조사할 질문을 나누고, 서브 리서처가 웹·공식 문서·이미지 등을 찾는다.
마지막에는 링크만 던져 주지 않고 확인된 사실, 참고 이미지, 출처, 모르는 내용을 함께 전달한다.
이름의 근거는 [참고 자료](./references.md), 크레인 요청 예시는
[자료 조사와 전달 예시](./research.md)에 있다.

## 3. 디자이너와 개발자는 어떻게 다른가?

- **웹 디자이너:** 화면 배치, 색상, 글자, 버튼 상태, 화면 크기별 모습을 설계한다.
- **Blender 디자이너:** 3D 모델, 재질, 조명, 필요한 움직임을 만들고 사용할 파일로 전달한다.
- **개발자:** 디자인과 3D 자산을 코드에 연결해 버튼·데이터·회전 같은 기능이 작동하게 한다.

예를 들어 3D 제품 소개 페이지라면 웹 디자이너는 페이지를, Blender 디자이너는
제품 모델을 만들고, Frontend 개발자는 모델을 웹에 띄워 회전·확대 기능을 연결한다.
UI 디자이너 Lead는 페이지와 모델의 분위기를 맞추고, 개발 Lead는 기술적으로 연결한다.

디자인팀의 검토는 의도 설명과 제출 전 점검이다. 디자인 일치 여부를 포함한 공식 결과
검증과 합격 판정은 QA가 맡는다. 예쁜 시안이나 렌더 이미지 하나만으로 완성 판정을 하지 않는다.

## 4. 실제 요청 하나가 진행되는 모습

당신이 “3D 제품을 돌려 볼 수 있는 소개 페이지를 만들어줘”라고 요청했다고 하자.

1. **총괄 PM:** 제품, 필요한 기능, 이번에 만들 범위를 정리한다. 중요한 선택만 당신에게 묻는다.
2. **리서치 Lead:** 필요한 제품 자료·제원·여러 각도의 이미지를 조사해 출처와 함께 전달한다.
3. **기획 Lead:** 방문자가 페이지를 열고 제품을 보고 정보를 확인하는 흐름을 정리한다.
4. **QA Lead:** 회전·확대, 작은 화면 사용, 모델 표시 등 합격 기준을 개발 전에 만든다.
5. **UI 디자이너 Lead + 개발 Lead:** 디자인 방향과 파일 형식·크기·성능 조건을 맞춘다.
6. **Orchestrator:** 조사·웹 디자인·Blender 제작·개발 등 준비된 작업을 나누어 배정한다.
7. **디자이너와 개발자들:** 승인된 기준 안에서 맡은 결과와 자체 점검 증거를 제출한다. Lead는 제출 준비를 돕는다.
8. **개발 Lead:** 웹·데이터·3D 자산을 하나의 확인 가능한 결과물로 모은다.
9. **서브 QA들 → QA Lead:** 실제로 사용해 검사한다. QA Lead가 판정하고 실패 항목은 담당 Lead를 거쳐 수정 작업으로 돌린다.
10. **총괄 PM:** QA가 승인한 범위와 미완료·남은 문제를 Codex 대화창으로 보고한다. 별도 품질 승인자가 아니다.

위 순서는 이해를 위한 설명이다. 실제로는 준비된 화면·스토리·기능부터 대량 병렬 실행하고,
그 결과의 QA·수정과 다음 작업의 제작을 겹쳐 진행한다. 서버가 디자인을 기다릴 필요는 없다.
반대로 파일 형식처럼 서로 맞춰야 하는 내용은 먼저 합의한다.

## 5. “동적 팀원”은 무슨 뜻인가?

동일한 역할을 가진 작업자를 업무 단위로 계속 추가할 수 있다는 뜻이다.
이 하네스는 소수 인원으로 끝내는 방식을 기본으로 하지 않는다.

- UI 디자이너 Lead의 공통 컨셉 아래에서 다수의 디자이너가 스토리·화면·상태별로 동시에 작업한다.
- Frontend Lead 아래에서 다수, 확장 목표로는 수백 명의 FE 개발자가 기능·기획 항목별로 동시에 작업한다.
- Blender는 자산·부품·장면·재질·움직임별로 나누고 같은 자산의 대안도 별도로 만들 수 있다.
- 리서처와 QA도 주제·출처·환경·시나리오별로 대량 병렬 실행한다.

같은 역할의 중복은 허용하지만, 같은 파일에 동시에 덮어쓰지는 않는다.
같은 과제의 여러 시안·구현은 분리된 후보로 만든다. Lead는 기준에 맞는 후보를 추천하고
QA가 합격 여부를 판정한다. 합격 후보 중 선호 선택과 새 통합 후보의 재검증은 R&R 규칙을 따른다.
합격한 후보라도 서로 조합하거나 수정하면 새 후보이므로 QA가 다시 검증한다.
새 인원이 필요할 때마다 사용자에게 묻지는 않되, 승인된 목표·권한·실제 자원 범위 안에서 운영한다.
모바일 범위가 없는 경우처럼 목표와 무관한 작업은 인원을 늘리기 위해 만들지 않는다.

## 6. “하네스”는 팀의 업무 규칙과 관리 장치다

쉽게 말해 업무 배정표, 작업 기록, 검수 절차를 합친 것이다.

- 같은 파일을 두 사람이 동시에 망가뜨리지 않게 한다.
- 무엇을 해야 완료인지 미리 적어 둔다.
- 검사하지 않은 결과를 완료라고 말하지 않게 한다.
- 실패하면 누구에게 돌려보낼지 정한다.
- 반복 실패를 끝없이 시도하지 않는다.
- 중간에 멈춰도 어디까지 했는지 확인하고 이어간다.
- Sub나 Lead가 확정된 기준을 뒤집거나 QA의 승인권을 대신하지 못하게 한다.

자세한 업무 순서와 Codex 내부 실행 설명은 [일하는 방법](./harness.md)에 있다.
책임자·작업자별 상세 범위는 [역할 설명](./roles.md), 조사 근거는
[참고 자료](./references.md), 조사팀의 결과물은 [자료 조사와 전달 예시](./research.md)를 읽으면 된다.
실행·변경·승인 권한과 팀 간 소통은 [R&R 및 소통 규칙](./responsibilities.md)에 정리했다.
실행 규모와 6~12시간 운영 원칙은 [대규모 병렬 운영](./operating-mode.md)에 정리했다.

## 7. 현재 어디까지 되었나?

현재 완료된 것은 **팀 구조와 운영 규칙의 문서화**다.
역할별 에이전트 설정, Blender 연결, 자동 실행·복구 장치, Discord 연결은
이 문서 작성에 포함되지 않는다. 실제 가동 전에 사용 가능한 도구와 권한을 확인해야 한다.
raphthon의 장시간 실행 관리자와 수백 개 동시 작업 지원도 아직 구현·검증하지 않았다.

Codex를 사용하는 기본 창구는 지금의 대화창이다. Discord가 필요하면 나중에
같은 팀으로 요청을 전달하는 별도 연결을 추가한다. Discord 봇이 총괄 PM이나
Orchestrator 자체가 되는 것은 아니다.
