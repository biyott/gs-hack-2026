## Evidence joins and limitations

Warmup and measured captures are separate. Evidence retains the raw injection, actual parsed boundary, immediate/before/final snapshots, ordered in-process bus snapshots, actual service inputs/results, full provider input/output events and returned vectors, provider identities, and database rows.

The exact E5 join requires one measured service invocation for the target's new profile and same run; one corresponding embedding start/completion; the exact attach-built query text; one real unit384-vector; one **new** retrieval row absent from the pre-command database; exact vector and embedding-identity equality; and the service's returned generation ID whose stored guidance ID and time interval bind that retrieval. Multiple overlapping calls, additional new retrieval rows, missing outputs or mismatches withhold the exact join. Capture ranges and vector similarity alone are insufficient.

The existing `captureProviders` helper forwards original texts/input and AbortSignal to actual provider methods, exposes their identity, returns successful provider values unchanged, and rethrows original provider errors. Its recording does create another promise at the provider boundary and performs cloning/hashing. Serialization failures can change observed failure behavior, capture work adds latency, and recorded elapsed time is not a clean product-deadline benchmark. The call index is only a local ledger key. Errors can include sensitive text; retain complete captures privately.

Its `settle()` snapshots currently tracked promises. This driver first drains actual initialization/enrichment promises and waits for terminal publication, then calls `settle()` and repeats if service-call count changed. Historical accepted `guidance.supplement` events count as terminal after a later profile replaces the guide. Failed or incomplete observation drains produce NOT_RUN. The existing 8092 provider and main-owned resident E5 remain owned by their original callers.
