## Marker and audit rules

The recovery marker is server intent scoped to the existing primary. No path can create `spokenAt`, `understoodAt`, a voice-completed/cancelled worker event, or a worker response receipt merely to make recovery appear successful. Existing facts remain unchanged. A CAS loser must not expose or persist its newly calculated timestamp; a real winner's earlier marker must not be erased to satisfy a blanket “no marker” assertion.

QD003-D1 says to preserve genuine audit facts, but does not mandate a newly named recovery AuditEvent or a minimum incident-audit row count. A successful engine snapshot revision is not a device observation. Do not invent a required `simulation.recovered` event or forbid every possible correctly attributed, atomically committed engine event. The bounded current implementation has no new recovery event insertion; final source binding can distinguish engine trace from existing worker/incident facts. Failure/loser paths must never leave a fabricated event attributed to an operation that did not commit.

Snapshot stream/sequence may change when a runtime is reconstructed. Keep those observations in the publication ledger, but exclude them from domain-delta/no-op assertions. Do not exclude run ID/version, updatedAt, marker, lineage or target metadata to hide a domain change.
