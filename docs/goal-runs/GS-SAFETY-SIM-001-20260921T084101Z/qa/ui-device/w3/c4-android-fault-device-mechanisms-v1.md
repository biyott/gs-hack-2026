## Actual wire selectors and ACK semantics

Select one genuine mobile request with method `POST`, pathname `/api/workers/${encodeURIComponent(workerId)}/response`, JSON `response == "voice-started"`, and an explicitly bound tuple `(mode, runId, workerId, incidentId, guidanceId, guidanceVersion, requestId)`. URL worker and JSON worker must agree. Fail closed on an unexpected worker, run, mode, content type, body, or second matching request. Preserve exact request bytes and `occurredAt`; do not synthesize an ACK or rewrite its identity.

The app sends these nine fields: `runId`, `mode`, `workerId`, `incidentId`, `guidanceId`, `guidanceVersion`, `response`, `requestId`, `occurredAt`. The contract also permits `detail`, but this mobile implementation does not supply it. For all `voice-*` responses, `guidanceVersion` is the event's `primaryGuidanceVersion`, including when a supplement is current. The stable request ID is `mobile/<runId>/<guidanceId>/<primaryGuidanceVersion>/voice-started`. Retries reuse the original request and original `occurredAt`. Pending or sent requests are locally deduplicated.

The body has no native utterance UUID, Dart playback generation, ACK generation, repository epoch, connection ID, installed APK identity, or device session ID. A bearer token is present in the HTTP header. Record a private token mapping or non-secret alias/hash if required; do not publish the token. Native UUID and any temporal pairing with guidance need separate evidence, and cannot be represented as an exact body-field join.

`voice-started` maps from Dart `SpeechStatus.playing`. Playback emits that status **before** awaiting `speech.speak(...)`. It is therefore evidence of the application's requested playback state, not Android `UtteranceProgressListener.onStart`, audible speech, or understood guidance. Vibration is independently requested and has no worker-response wire kind.

## Two distinct hold/release cases

1. **Hold the actual request before any upstream send.** Keep the mobile socket open. Record capture, first upstream forwarding, downstream release/close, exact request hash, and whether the client remained connected. A release after an authoritative new primary or run reset tests the server's rejection of stale identity. If the request has never committed and the incident remains open, stale guidance is expected to yield HTTP 409 `STALE_GUIDANCE`; a missing incident can instead yield 404 `NOT_FOUND`, a closed incident can yield 409 `INVALID_TRANSITION`, and a revoked/expired session can fail authentication earlier. Record the actual reason. An exact already-committed receipt is replayed before stale checks and may return 200, so absence of prior commitment is a prerequisite for the stale-first-send case.
2. **Forward the genuine request once, then hold only its real upstream response.** This tests late client completion handling after a genuine server acceptance. After a new current event, the coordinator's identity check suppresses publishing the old ACK status into the new event's state. A run/profile/worker reset also increments the ACK generation, and disposal invalidates pending completions. The old request can be successfully committed upstream while its late completion is correctly ignored locally; these are separate observations. The mobile ACK service discards the returned snapshot, so releasing the old response body does not itself adopt its guidance.

The API request has one 12-second total timeout. Release within that lifetime, with margin and a recorded surviving downstream socket, to exercise a delivered late completion. Holding through the deadline exercises timeout/abort handling. Once the request is aborted, an attempted proxy write is not evidence the app received a late completion. Do not silently retry or reclassify it.

## Normal stop-intent sequence

Use the real authenticated control endpoint `POST /api/simulation` with `{ "mode": <bound mode>, "action": "pause", "expectedVersion": <fresh run.version>, "requestId": <unique ID> }`. There is no simulation `stop` action and no `voice-stopped` worker response. Preserve any actual version-conflict response; a future harness must not silently repair the test case.

Pausing calls `requestPlaybackStop`. A worker with guidance and `voiceStatus == pending` keeps `pending` and receives `voiceStopRequestedAt`; one with `playing` becomes `stop-requested`. Existing completed/failed/unsupported states are preserved. The phone receives the real paused snapshot, disables playback, and suspends outputs. If the genuine, never-forwarded `voice-started` request is then released while the same guidance is still current and unexpired, the server sees the stop-intent marker (or non-running status) and yields `stop-requested`, not `playing`. The marker also survives a normal `resume`, so pause → resume → delayed request is a separate useful case.

This requires no intervening new primary, expiry, completion/failure receipt, or session replacement; otherwise another branch legitimately controls the result. Receiving a `voice-completed` or `voice-failed` message before the delayed start may preserve that terminal state rather than produce `stop-requested`. A phone lifecycle pause/background action stops local outputs and its repository subscription, but does not itself issue the server's simulation pause command. Do not attribute a server stop-intent record to a local lifecycle action alone.

## Complete snapshot framing and accepted ordering

The real SSE endpoint is `GET /api/events?mode=<bound mode>`. A publication is a complete frame: `id: <streamId>:<mode>:<sequence>`, `event: snapshot`, and `data: <complete scoped snapshot JSON>`, terminated by a blank line. Preserve the complete envelope and all fields outside the declared transform. The mobile parser uses `event:` and `data:` but does not use the SSE `id:` line for ordering. The JSON `streamId` and integer `sequence` control repository acceptance.

First GET `/api/simulation` validates metadata but cannot establish a previously unknown stream. The first valid SSE frame can establish it through `bootstrap: true`. Same-stream sequences at or below the last accepted sequence are discarded before session parsing or guidance guarding. A different stream is accepted only at a connection's SSE bootstrap and only if it is not retired. Thus a stream-ID substitution midway through a connection does not exercise an inner guidance rejection. Keep the selected mode, contract version `1.0.0`, real stream ID, and actual publication sequence intact for inner cases.

For each inner case: ARM on an already-established connection, withhold the next **actual** complete upstream snapshot N greater than the last forwarded N−1, freeze its original bytes and transformed complete-envelope bytes, then inject the transformed N once. Buffer/suppress subsequent upstream frames until explicit RECOVER; preserve their counts and identities. On RECOVER, forward the newest actual later N+k and resume normal traffic. Do not invent a higher sequence or silently renumber normal publications. If reconnect occurs during the controlled interval, record the case as interrupted/inconclusive rather than continuing under an assumed identity.

Duplicate and reversed-sequence cases instead replay exact previously forwarded complete envelopes on the same established connection. Replaying N then older N−1 should not re-adopt either snapshot, repeat received ACKs, or replay output. Those are repository cases; they do not prove the inner guidance guard ran.

## Recovery and unobservable boundaries

RECOVER proves a transport action, not automatically a UI recovery. `clearCurrent()` and map invalidation do not clear the guard's event/version history. A later original snapshot carrying the same already-seen event remains duplicate and does not restore an invalidated/cleared current. Require an actually new valid primary from a normal server action or an explicit session logout/reconnect that constructs a new coordinator, and record that extra action. Do not silently reset between injection and the failure observation.

Native stop clears the Android utterance registry before queued callbacks run; callback dispatch checks membership again on the platform thread. Dart speech, playback, ACK, repository, and session layers have separate ownership/generation checks. The transport proxy can arrange delayed request/response and SSE delivery; it cannot inject an obsolete Android `onStart`, `onDone`, or `onError` callback into that registry, nor prove such a callback was delivered and rejected. Absence of an old callback log is not that proof. `UtteranceRegistry` UUIDs are not exported in ACK JSON. Any native UUID/time association must state its observational limits.

The proxy also cannot force `isLanguageAvailable == false`, native TTS engine failure, or physical vibration failure. An HTTP failure of a `voice-started` POST is an acknowledgement transport failure, not a TTS failure. The vibration service requests a 350 ms vibration; a returned future or UI status does not prove it was felt. Heard speech, interruption heard, language intelligibility, and felt vibration require run/guidance/version/UTC-bound human evidence through the QA lead under the actual device grant. Obsolete native callback injection, controlled engine/language failures, and felt vibration remain NOT RUN by this mechanism. Camera access is not needed for any case in this note.
