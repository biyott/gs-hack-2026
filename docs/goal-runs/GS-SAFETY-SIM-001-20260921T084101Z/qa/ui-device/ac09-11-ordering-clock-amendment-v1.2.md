## Published ordering binding

docs/contracts/v1.0.1-addendum.md now publishes `streamId` as a fresh application-server-runtime UUID and `sequence` as a nonnegative safe integer increasing per mode throughout that runtime, including run resets and transient tracking changes. HTTP and SSE snapshots share the ordering. Changed visible state needs a higher sequence; identical repeated publication may keep its sequence. Persisted `run.version` is an optimistic mutation revision, not publication order.

Within a mode and established stream, a client accepts only a strictly higher sequence, regardless of runId. HTTP responses cannot switch an established stream. Only the first authoritative snapshot from the currently owned initial/reconnected SSE connection can establish a new stream baseline; callbacks from superseded connections are ignored. New stream after server restart may restore an older persisted mutation revision truthfully. Old persisted snapshots may parse with legacy/0 defaults for migration; actual new wire snapshots must be stamped with real runtime identity and sequence.

These rules are independent of primary speech identity `(runId, workerId, guidanceId, primaryGuidanceVersion)`. Receiving a new snapshot or supplement envelope is not itself a new primary speech action.
