# Hermes 개발 에이전트 팀 설계

작성일: 2026-09-21

이 문서는 Discord를 사용자 창구로 사용하고 WSL에서 개발 작업을 수행하는
Hermes 팀의 권장 책임 구조와 운영 원칙을 정리한다.
**설계 제안이며, 에이전트 생성이나 Hermes 설정 적용을 완료했다는 의미는 아니다.**
공식 자료의 주장과 이 프로젝트에 적용한 판단은
[참고 자료 및 적용 근거](./references.md)에서 구분한다.

## 1. 핵심 결정

- 총괄 PM과 Orchestrator는 분리한다.
- 총괄 PM은 현재 단일 프로젝트의 Product PM 역할도 겸한다.
- 기존 개발 PM은 Engineering Lead, 분야별 PM은 분야별 Lead로 명명한다.
- 기획 Lead 아래에 필요에 따라 서브 기획자를 배정한다.
- 개발자와 독립 검증자는 작업 단위로 동적으로 투입한다.
- 고정 역할 정의를 유지하는 것과 모든 에이전트를 상시 실행하는 것은 구분한다.
- 조직의 책임 관계를 그대로 깊은 런타임 호출 계층으로 구현하지 않는다.

앞선 논의에서 총괄 PM을 Product PM으로 바꾸어 설명한 부분은 이 문서로 정리한다.
총괄 PM은 없어지는 것이 아니다. 사용자 의도와 제품 의사결정의 책임자로 유지한다.

## 2. 권장 책임 구조

```text
사용자
  ↕ Discord 봇 — 대화 창구
총괄 PM
  ↕ 목표·우선순위·승인 / 진행·문제·결과 보고
Orchestrator — 전체 실행 조정
  ├─ 기획 Lead
  │    └─ 서브 기획자 [필요할 때 생성]
  │         요구사항 / 사용자 흐름 / 정책·예외 / 리서치
  ├─ Engineering Lead
  │    아키텍처 / API 계약 / 공통 기술 결정 / 통합 책임
  ├─ Frontend Lead
  │    └─ Frontend Developer [필요한 수만 생성]
  ├─ Backend Lead
  │    └─ Backend Developer [필요한 수만 생성]
  ├─ Mobile Lead
  │    └─ Mobile Developer [필요한 수만 생성]
  └─ 독립 검증 에이전트 [필요할 때 생성]
       코드 리뷰 / 통합 QA / 보안 검토
```

이 그림은 책임 관계도이지 필수 호출 순서가 아니다. Engineering Lead는 모든
메시지를 중계하는 관리자가 아니라 공통 기술 결정과 통합 판단을 담당하는 전문가다.
분야별 Lead도 필요 없는 작업에서는 호출하지 않는다.

Discord 봇은 접근 창구이고 PM은 내부 역할이다. 이 설계에서는 봇의 대표 응답자를
총괄 PM으로 연결한다. 내부 역할마다 별도의 Discord 봇을 만들 필요는 없다.
실제 프로필 라우팅과 내부 위임 연결은 구현 단계에서 확인한다.

## 3. 역할과 권한

| 역할 | 책임과 결정권 | 주요 산출물 | 경계 |
| --- | --- | --- | --- |
| 총괄 PM | 사용자 의도, 범위·우선순위·완료 기준 관리, 변경 승인 요청, 최종 보고 | 작업 목표, 우선순위, 승인 기록, 완료 보고 | 실행 프로세스의 생성·재시도를 직접 관리하지 않는다. |
| Orchestrator | 작업 배정, 의존성·상태 관리, 동시 실행 제한, 실패 복구, 결과 수집 | 작업 목록, 실행 기록, 차단 사유, 증거 링크 | 제품 범위·우선순위를 임의 변경하지 않는다. |
| 기획 Lead | 상세 명세 작성, 서브 기획 결과 통합, 모순 해결 | 요구사항 명세, 사용자 흐름, 정책, 인수 기준 | 사용자 승인 없이 제품 범위를 확대하지 않는다. |
| 서브 기획자 | 배정된 주제의 조사·분석·구체화 | 요구사항 분석, 흐름, 정책·예외 목록, 조사 근거 | 독립적인 전체 기획안을 각각 확정하지 않는다. |
| Engineering Lead | 시스템 구조, API·데이터 계약, 기술 충돌 해결, 통합 판단 | 아키텍처 결정, 인터페이스 계약, 통합 기준 | 단순 진행 전달만 하는 중간 관리자가 되지 않는다. |
| 분야별 Lead | 분야별 작업 분할, 소유 영역 지정, 기술 검토 | 구현 작업 명세, 파일 소유권, 검토 결과 | 다른 분야의 계약이나 공통 파일을 독단적으로 변경하지 않는다. |
| 개발자 | 지정된 범위의 구현·테스트·결과 제출 | 코드 변경, 테스트 결과, 남은 문제 | 범위 확장이나 무제한 재위임을 하지 않는다. |
| 독립 검증자 | 요구사항 충족, 회귀·보안·통합 검증 | 재현 가능한 검증 기록과 통과·실패 판정 | 구현자의 완료 보고만으로 통과시키지 않는다. |

최종 제품 범위 변경과 외부에 영향을 주는 중요한 작업의 승인권은 사용자에게 있다.
총괄 PM은 위임받은 범위 안에서 판단하고, 범위를 벗어나면 사용자에게 결정을 요청한다.

### 총괄 PM과 Product PM

현재는 단일 프로젝트를 전제로 총괄 PM이 제품 요구사항과 우선순위도 담당한다.
여러 제품의 독립적인 로드맵과 이해관계자를 관리해야 할 때 별도 Product PM을 검토한다.
역할의 이름을 늘리는 것 자체가 품질이나 병렬성을 높이지는 않는다.

### Lead와 Orchestrator

Lead는 해당 전문 분야에서 작업을 어떻게 나눌지 제안하고 결과의 품질을 판단한다.
Orchestrator는 전체 작업의 실행 여부·순서·자원 배정을 통제한다.
초기에는 Lead가 작업자 생성을 요청하고 Orchestrator가 실행하도록 구성한다.
향후 Lead의 직접 생성 권한을 허용하더라도 중앙 실행 한도 안에서만 허용한다.

## 4. 작업 흐름

회원가입 기능을 예로 든다.

1. 총괄 PM이 로그인 방식, 필수 범위, 완료 기준과 미결정 사항을 정리한다.
2. Orchestrator가 기획 Lead에게 상세화를 배정한다.
3. 기획 Lead는 필요하면 사용자 흐름과 정책·예외 담당 서브 기획자를 요청한다.
4. Engineering Lead가 API, 데이터 구조, 인증 방식의 공통 계약을 정한다.
5. 계약을 기준으로 Frontend·Backend·Mobile 작업 중 필요한 분야를 병렬 실행한다.
6. 각 Lead가 분야 결과를 검토하고 Engineering Lead가 통합 문제를 조정한다.
7. 독립 검증자가 실제 가입 흐름, 실패 사례, 회귀와 보안 조건을 확인한다.
8. 총괄 PM이 완료 범위, 남은 문제와 사용자 확인 사항을 Discord로 보고한다.

명세나 API 계약 변경이 필요하면 관련 작업을 멈추거나 재계획한다.
작업자가 각자 서로 다른 계약을 가정한 상태로 계속 구현하지 않는다.

작은 문구 수정은 기획·아키텍처 단계를 생략하고 해당 작업자와 검증자만 호출한다.
모든 작업을 모든 역할에게 순차적으로 통과시키는 결재선은 만들지 않는다.

## 5. 동적 작업자 운영 규칙

### 작업마다 전달할 계약

| 항목 | 내용 |
| --- | --- |
| 작업 ID와 목표 | 한 작업의 식별자와 구체적인 완료 목표 |
| 입력 | 승인된 명세, 관련 코드, API 계약, 선행 결과 |
| 소유 영역 | 수정 가능한 파일·모듈과 다른 작업자와의 경계 |
| 산출물 | 코드, 문서, 테스트 결과 등 제출해야 할 결과 |
| 완료 기준 | 재현 가능한 검증 방법과 통과 조건 |
| 제약 | 재위임 허용 여부, 실행 한도, 금지 작업, 승인 조건 |
| 의존성과 보고 | 기다릴 작업, 차단 시 보고 대상, 결과 저장 위치 |

### 병렬성·충돌 관리

- 독립적인 작업만 병렬 실행하고 의존 작업은 선행 결과를 기다린다.
- 같은 파일을 여러 작업자가 동시에 수정하지 않도록 소유권을 배정한다.
- 공통 계약·공유 파일의 변경은 Engineering Lead와 관련 Lead가 조정한다.
- 작업별 브랜치나 worktree를 사용한다면 실제 경로와 격리 상태를 확인한다.
- 격리는 통합 충돌을 없애지 않으므로 결과 통합과 회귀 검증을 별도로 수행한다.
- 전역 동시 실행 한도는 Orchestrator가 관리한다. 부모별 생성 한도와 혼동하지 않는다.
- 단순 재시도 횟수를 제한하고 반복 실패는 원인과 증거를 기록해 상위 역할로 보고한다.

구체적인 동시 실행 수는 실제 작업 부하와 사용 가능한 모델 한도를 측정한 뒤 정한다.
많은 에이전트를 띄우는 것보다 중복 작업과 불필요한 컨텍스트 전달을 줄이는 것이 우선이다.

### 상태 보존과 완료 판정

작업 목록, 의존성, 담당자, 결정 사항, 산출물 경로와 검증 결과를 대화 밖의 지속적인
작업 기록에 저장한다. 상태는 최소한 대기·실행 중·차단·검증 중·완료·실패로 구분한다.

프로세스가 재시작되었을 때 작업 기록이 있다고 실행 중인 에이전트가 자동 복원되는
것은 아니다. 남은 작업과 이미 수행한 외부 작업을 확인한 뒤 중복 실행 없이 재개한다.
완료 판정은 구현자의 선언이 아니라 명세와 검증 증거를 기준으로 한다.

## 6. 초기 구성과 구현 전 확인

고정 역할 정의는 총 7개다.

1. 총괄 PM
2. Orchestrator
3. 기획 Lead
4. Engineering Lead
5. Frontend Lead
6. Backend Lead
7. Mobile Lead

서브 기획자, 개발자, 독립 검증자는 동적으로 투입한다.
모바일 작업이 없는 경우 Mobile Lead를 활성화할 필요가 없다.
고정 역할을 모두 별도 상시 프로세스로 실행할 필요도 없다.

Hermes에 적용하기 전 다음을 검증한다.

- [ ] Discord 요청이 의도한 총괄 PM 프로필에 연결되는가?
- [ ] 총괄 PM과 Orchestrator 및 전문 역할 사이의 호출 방식이 지원되는가?
- [ ] 고정 프로필과 동적 하위 에이전트의 컨텍스트·인증·도구 범위가 의도와 맞는가?
- [ ] 중첩 위임 깊이와 동시 실행 제한의 실제 적용 범위를 확인했는가?
- [ ] 모든 생성 경로에서 전역 실행 한도를 지킬 수 있는가?
- [ ] 작업 경로, 파일 소유권, 결과 통합 담당이 명확한가?
- [ ] 대화 외부의 작업 기록과 실패·재시작 시 재개 절차가 있는가?
- [ ] 검증 실패 시 수정으로 돌아가는 경로가 있는가?
- [ ] 중요한 변경·배포·외부 작업의 사용자 승인 조건이 정해져 있는가?
- [ ] 토큰·인증 정보가 문서나 Git에 저장되지 않는가?

프롬프트에 조직도를 적는 것만으로 프로필 간 통신, 상태 공유, 중첩 위임이 자동으로
구성되지는 않는다. 위 항목은 설치된 Hermes 버전에서 검증해야 하며, 이 문서는
특정 설정 키나 실행 명령의 동작을 보장하지 않는다.

## 7. 평가와 구조 변경 기준

대표 작업 몇 개로 단일 에이전트 방식과 제안 구조를 비교한다.
완료율, 요구사항 누락, 회귀, 재작업 횟수, 소요 시간, 모델 사용량과 사용자 개입
횟수를 함께 기록한다. 성공 사례 하나만으로 구조가 검증되었다고 판단하지 않는다.

전달만 하는 역할은 통합하고, 반복적으로 과부하가 생기는 전문 영역만 분리한다.
병목과 실패 원인이 실제로 확인될 때 관리 계층이나 작업자 수를 늘린다.

최종 원칙은 **총괄 PM이 제품 의도를 지키고, Orchestrator가 실행을 통제하며,
전문 Lead와 동적 작업자가 필요한 일만 수행하는 구조**다.
