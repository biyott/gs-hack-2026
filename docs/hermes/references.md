# Hermes 팀 설계 참고 자료 및 적용 근거

정리일: 2026-09-21

[팀 설계 본문](./README.md)은 아래 공식 기술 자료를 참고한 프로젝트별 제안이다.
자료가 특정한 PM 조직도나 Hermes의 구현 방법을 직접 권장한다고 해석하지 않는다.
링크는 변경될 수 있는 웹 문서이며 특정 버전의 내용을 보존한 스냅샷은 아니다.

## 1. Anthropic: Building effective agents

- 발행 주체: Anthropic
- 유형: 에이전트 설계 엔지니어링 가이드
- 링크: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

### 자료의 핵심

가능한 단순한 해결 방법에서 시작하고 필요할 때 복잡성을 추가한다.
미리 정해진 workflow와 동적으로 판단하는 agent를 구분한다.
Orchestrator-workers 패턴은 중앙 역할이 작업을 나누어 위임하고 결과를 통합한다.
독립적인 작업에는 병렬 처리를, 명확한 평가 기준이 있는 작업에는 평가·개선 루프를
적용할 수 있다.

### 이번 설계에 적용한 판단

모든 요청이 모든 관리자 역할을 거치도록 만들지 않는다.
작은 수정은 짧은 실행 경로를 사용하고 복잡한 작업에만 전문 역할을 투입한다.
구현과 독립 검증을 구분한다.

### 해석의 한계

이 자료는 총괄 PM과 Orchestrator를 반드시 별도 에이전트로 만들라고 요구하지 않는다.
둘의 분리는 제품 의사결정과 실행 통제를 구분하려는 사용자의 요구에 따른 선택이다.

## 2. Anthropic: How we built our multi-agent research system

- 발행 주체: Anthropic
- 유형: 멀티에이전트 연구 시스템 구축 경험
- 링크: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### 자료의 핵심

리드 에이전트가 작업을 분해하고 전문 하위 에이전트의 결과를 모으는 방식을 설명한다.
위임 목표, 산출물 형식, 도구와 작업 경계가 불명확하면 중복과 누락이 발생한다.
코딩처럼 의존성과 공유 컨텍스트가 많은 작업은 독립적인 조사보다 병렬화가 어렵다.
과도한 위임과 조정 비용도 고려해야 한다.

### 이번 설계에 적용한 판단

동적 작업자에게 구체적인 작업 계약을 전달한다.
개발자 수를 늘리기 전에 파일 소유권과 인터페이스를 정하고, 기획 조사처럼 독립적인
작업과 공유 코드를 변경하는 작업을 다르게 취급한다.

### 해석의 한계

연구 시스템의 성과나 모델 사용량을 Hermes 개발 팀의 기대 수치로 전용할 수 없다.
이 자료가 다단계 개발 관리 조직의 우월성을 입증하는 것은 아니다.

## 3. Microsoft: AI agent orchestration patterns

- 발행 주체: Microsoft Azure Architecture Center
- 유형: 아키텍처 설계 가이드
- 링크: [AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)

### 자료의 핵심

요구사항을 충족하는 가장 낮은 복잡도에서 시작한다.
순차 처리는 단계 사이의 의존성이 있을 때, 병렬 처리는 독립적인 작업에 적합하다.
동시 실행 시 공유 상태 충돌, 모델 자원 제약과 결과 통합 문제를 고려해야 한다.
그룹 대화 패턴은 토론과 공동 검토 등에 활용할 수 있지만 모든 실행 작업의 기본
형태로 적합한 것은 아니다.

### 이번 설계에 적용한 판단

기획과 공통 계약을 선행한 뒤 독립적인 개발 작업을 병렬 실행한다.
중앙 실행 한도와 충돌 처리 규칙을 둔다.
모든 역할이 하나의 긴 대화에서 계속 토론하는 형태를 기본 실행 방식으로 삼지 않는다.

### 해석의 한계

일반적인 아키텍처 패턴 설명이지 Hermes의 프로필 간 통신이나 위임 깊이를 보장하는
제품 문서는 아니다. 실제 지원 기능은 별도 확인해야 한다.

## 4. Microsoft ISE: Orchestration Patterns for Multi-Agent Systems

- 발행 주체: Microsoft Industry Solutions Engineering
- 작성자: Lily Jia
- 발행일: 2026-06-12
- 유형: 실제 고객 프로젝트의 구조 전환과 비용에 대한 경험 보고
- 링크: [Orchestration Patterns for Multi-Agent Systems: Performance and Trade-offs](https://devblogs.microsoft.com/ise/coordinator-patterns-multi-agent-systems/)

### 자료의 핵심

Coordinator가 독립적인 도메인 에이전트를 순차 또는 병렬 호출하고 결과를 통합한다.
이 구조는 재사용과 책임 분리에 유리하지만 조정·호출·종합 과정에 지연이 생긴다.
해당 사례는 초기 성능 점검을 보고하며, 프레임워크 사이의 비교 벤치마크를 완료한
결과로 제시하지 않는다.

### 이번 설계에 적용한 판단

Orchestrator와 전문 Lead 사이의 입력·출력 경계를 명확히 한다.
작은 요청에는 전체 조직을 호출하지 않고 실제 지연과 결과 품질을 측정한다.

### 해석의 한계

소매 분야의 마이크로서비스 기반 챗봇 사례다. 한 PC에서 실행되는 Hermes 개발 팀과
동일하지 않으며, 이 사례를 근거로 각 역할을 별도 서비스로 배포할 필요는 없다.

## 5. 근거와 설계 결정의 대응

| 설계 결정 | 근거 또는 이유 | 구분 |
| --- | --- | --- |
| 불필요한 관리 계층을 줄인다. | Anthropic 설계 가이드, Microsoft 아키텍처 가이드 | 자료의 원칙 적용 |
| 독립 작업만 병렬화한다. | Anthropic 연구 시스템, Microsoft 아키텍처 가이드 | 자료의 원칙 적용 |
| 목표·산출물·작업 경계를 명시한다. | Anthropic 연구 시스템 | 자료의 원칙 적용 |
| 총괄 PM과 Orchestrator를 분리한다. | 제품 의사결정과 실행 통제를 분리하려는 사용자 요구 | 프로젝트별 설계 판단 |
| 총괄 PM이 Product PM을 겸한다. | 현재 단일 프로젝트에서 중복 관리 역할을 줄임 | 프로젝트별 설계 판단 |
| 개발 PM을 Engineering Lead로 명명한다. | 기술 계약·통합 책임을 명확하게 표현 | 프로젝트별 설계 판단 |
| 기획 Lead와 동적 서브 기획자를 둔다. | 기획 통합 책임은 고정하고 세부 작업은 필요에 따라 분리 | 프로젝트별 설계 판단 |
| 고정 역할 7개와 동적 검증자를 사용한다. | 요청한 전문 영역을 보존하면서 상시 실행을 줄임 | 초기 제안, 효과 측정 필요 |
| Discord 봇 하나를 대표 창구로 사용한다. | 사용자 접점과 내부 역할을 구분 | 구현 가능 경로 확인 필요 |

## 6. 구현 검증과 구분할 사항

위 자료들은 Hermes의 현재 설치 버전, Discord 라우팅, 프로필 간 호출, 인증 상속,
하위 에이전트 재위임과 작업 경로 격리를 검증하지 않는다.
이 문서에는 해당 기능을 확인하지 않은 상태에서 바로 적용할 설정값을 제시하지 않는다.

구현 시에는 설치된 버전의 공식 문서와 실제 동작을 확인하고 검증한 버전, 설정,
테스트 결과를 별도의 운영 기록에 남긴다. 설계 역할 수와 실제 동시 실행 수 역시
다르게 관리해야 한다.
