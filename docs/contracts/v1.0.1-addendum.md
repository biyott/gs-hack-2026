# Contract revision 1.0.1 addendum

Technical owner: `/root/tech_lead`. This addendum extends the preserved [v1 baseline](v1.md); original freeze hashes remain in `freeze-v1.0.0.json`. The wire simulation snapshot remains version1.0.0. Equipment catalog version1.0.1 adds backward-compatible articulation metadata. Source outcome, six equipment presets, map scale, safety policy and QA thresholds are unchanged.

## Snapshot publication order

The simulation snapshot adds `streamId` and `sequence`. `streamId` is a fresh UUID for each application-server runtime. `sequence` is a nonnegative safe integer, increasing for every published state within each simulation mode throughout that runtime, including run resets and transient tracking updates. It does not reset when `runId` changes. HTTP snapshots and SSE snapshots share this ordering. Repeated delivery of an identical publication may retain its sequence; changed visible state must receive a higher sequence. `run.version` remains the persisted optimistic mutation revision and cannot order high-frequency publications.

Within the same mode and stream, clients accept only a strictly higher sequence, regardless of run ID. This rejects duplicate and out-of-order SSE messages and a delayed old-run HTTP mutation response after a reset. HTTP responses cannot switch an established stream. Only the first authoritative snapshot from the currently owned initial/reconnected SSE connection may establish a new stream baseline; callbacks from a superseded connection are ignored. A server restart can restore a checkpoint with an older persisted revision, and the fresh stream identity makes this explicit. Backend, Frontend and Mobile Leads own matching producer/consumer regressions, including reversed messages and delayed old-run HTTP responses.

Before the first owned SSE baseline, HTTP snapshots remain pending or are ignored; they cannot establish a stream or be presented as authoritative current state. A reconnect preserves the accepted watermark until its first valid snapshot: the same stream still requires a higher sequence, while a different stream may establish a new baseline. A valid higher-sequence snapshot may introduce a new run, but every contained worker guidance must still match its envelope's run and worker identity. Stream ordering does not relax guidance binding or expiry checks.

The schema defaults absent ordering fields to `streamId:"legacy"` and `sequence:0` solely so an old persisted snapshot can be parsed and migrated. The server must stamp a real runtime UUID and current sequence before exposing any restored snapshot. New wire responses always carry both fields. Additive snapshot fields keep wire `contractVersion:"1.0.0"`; this document revision records the stronger publication contract.

`SimulationWireSnapshotSchema` is the HTTP/SSE boundary and requires both fields with a real UUID, rejecting legacy defaults. `SimulationSnapshotSchema` retains the persistence migration defaults. SSE event IDs are `streamId:mode:sequence`; the parsed envelope fields determine acceptance. A persisted idempotency receipt proves a mutation was already applied; returning it must not relabel historical state with a current publication sequence.

## Equipment articulation

Design, Frontend and Backend Leads concurred on the machine-readable rig structure. `EquipmentPreset.articulation` is nullable; older catalogs normalize its absence to null. `EquipmentCatalogSchema` accepts1.0.0 and1.0.1. `EquipmentArticulationSchema` in `packages/contracts/src/articulation.ts` owns the exact fields and rejects reversed links, undefined axes and invalid scale ratios.

- `boom`: `pivotNode`, local `axis:"z"`, `angleSign:1`, `tipNode`, and telescopic `segments[{node,axis:"x",lengthShare}]`.
- `hook`: `node` and `tipNode`.
- `links`: `node`, `fromNode`, `toNode`, `startFraction`, `endFraction`, local `axis:"y"`, `restLengthM`, `origin:"start"`.

Boom rotation is the original local Z angle plus the selected-minus-baseline angle. Each segment's local X displacement is selected-minus-baseline boom length multiplied by its length share. After updating transforms, the hook world X/Z follows its tip and world Y follows the selected hook height; convert the result into the hook parent's local coordinates. Links use normalized +Y geometry, position at their selected anchor fraction, rotate +Y toward the anchor delta and scale by actual span divided by rest length. Model meshes never become collision-authority geometry.

Required motions above are a requirement inventory, not implementation/QA evidence. Current asset implementation is recorded by `controls`, `verificationStatus` and rig tests; engine-supported geometry is recorded separately in `riskGeometry`, `riskGeometryStatus` and engine tests. A visual control does not certify hazard geometry. Exact unknown tower support coordinates remain null; nominal4.6m support width does not invent an exterior polygon.

The [authoritative control boundary](../../src/server/simulation/equipment-controls.ts) rejects unsupported controls (`UNSUPPORTED_CONTROL`), selected-configuration limits (`CONTROL_LIMIT`) and origins outside the140m×50m map (`MAP_BOUNDS`) before changing state. Accepted pose changes increment `geometryVersion` and trigger the runtime's hazard, route and guidance evaluation. The [analytic equipment geometry](../../src/server/engine/equipment.ts) transforms chassis parts by heading, upper/load parts by heading plus slew, and predicts translation from speed and the policy horizon. Hook planar reach is trolley distance or boom length×cos(boom angle). Hook height affects the visual hoist while the conservative ground-plane load footprint remains; this2D model does not claim certified3D load-clearance analysis. Catalog `riskGeometryStatus:"verified"` records tests of synthetic demo geometry, not manufacturer safety certification.

## Tracking and native pairing routes

All routes require authenticated sessions. Uploads are JSON. JPEG download is a media response. A phone's physical model does not grant a role or capability.

| Route | Contract / authorization |
| --- | --- |
| GET `/api/tracking` | `TrackingSnapshotSchema`; authenticated view of latest camera/UWB observations, calibration and counters; never includes UWB session keys |
| POST `/api/tracking/frame` | `FrameUploadSchema`; canonical singular path used by the mobile camera; CCTV role for live frames, administrator/operator for explicitly synthetic test frames |
| GET `/api/tracking/frame` | Latest JPEG; administrator/operator/observer or authenticated device |
| POST `/api/tracking/uwb` | `UwbUploadSchema`; authenticated EQUIPMENT Controller uploads two distinct worker observations under its current ready pairing epoch; administrator/operator tooling is explicitly synthetic |
| POST `/api/tracking/calibration` | `CalibrationSchema`; administrator/operator |
| POST `/api/uwb/prepare` | `UwbPreparedRegistrationSchema`; authenticated EQUIPMENT, WORKER_1 or WORKER_2 matching the stored role |
| DELETE `/api/uwb/prepare?generation=N` | Withdraw the authenticated participant's matching native generation; stale cleanup cannot remove a replacement participant |
| GET `/api/uwb/config` | Waiting/unsupported state or `UwbParticipantConfigSchema`; only an authenticated matching participant receives its required session key/configuration |
| GET `/api/clock` | Authenticated `ServerClockSchema` server UTC observation for bounded capture-time synchronization |

`/api/uwb/session` may be a compatibility alias; the native client canonical paths are prepare/config. One Controller and both Controlees register actual hardware capabilities before a multicast configuration is issued. Session keys are transient, excluded from snapshots/logs/evidence, and never stand in for actual device measurements.

Tracking uses per-camera frame sequence and per-worker UWB sequence/session epoch rather than run mutation revisions. Duplicates and reversed observations are rejected. Concurrent JPEG decoding drops a new frame as busy instead of building an unbounded queue. Calibration/session reset advances an epoch so an earlier in-flight decode cannot alter new state. A position becomes stale after1000ms without observation and loses its usable XY; range-only UWB keeps range evidence with nullable XY. These source-state changes remain separate from guidance/user acknowledgements. High-frequency latest state and the backend's one-second DB checkpoint are separate from immediate semantic incident history.

A native camera uploader sends its per-uploader UUID as `FrameUpload.streamId`, preserved in `CameraFrame.streamId`. A restarted uploader can restart its sequence at zero under a new identity without clearing calibration. Capture times remain globally monotonic for that camera, a newly observed stream cannot begin with a capture already older than1000ms, and retired streams cannot become current again. The optional field only preserves legacy upload compatibility; current native uploaders always provide it. This camera stream identity is independent of the application-server snapshot stream identity.

Recalibrating the same camera preserves ordering watermarks and retired stream identities while clearing visible observations and invalidating in-flight decoding through the calibration epoch. Selecting a different camera, explicitly resetting the tracking service or constructing a new service starts a fresh ordering lifetime. The first capture after any such reset must also satisfy the1000ms freshness bound.

Measurement technique and input authenticity are separate fields. `PositionObservation.source` identifies camera-marker or UWB processing; `inputSource` identifies `live`, `synthetic` or `unknown`. Worker/equipment snapshots preserve this distinction as `positionSource` and `positionInputSource`. Missing legacy authenticity normalizes to `unknown`, never to `live`. The authenticated upload boundary determines authenticity: actual device uploads are live, administrator/operator fixtures are synthetic, and scenario-generated positions are synthetic. Client interfaces preserve these labels through markers and observation panels. A request's self-declared source cannot authorize a live measurement claim.

Each mode's persisted run independently selects `positionInput:"scenario"|"measured"`, defaulting to `scenario` for new and migrated runs. Administrator/operator command `{action:"position-input",input,mode,expectedVersion,requestId}` changes that selection with the same concurrency, audit and persistence rules as other simulation commands and immediately recomputes affected hazards/routes/guidance. In scenario mode, physical uploads remain observable evidence and CCTV remains viewable, but uploads cannot overwrite scripted actor positions. In measured mode, missing or stale measurements produce unknown positions without falling back to scenario positions. Input selection and authenticity are independent: a synthetic tracking fixture remains synthetic when selected through measured mode.

The fixed tower retains its authored crane origin when the equipment phone moves; its fixed position is not relabeled as a live measurement. Workers can still use measured positions. Manual position changes cannot override the measured input selection. Slew, boom, trolley and hoist controls retain their selected model's capability/limit checks.

JPEG requests bind `cameraId`, `frameId`, `sequence` and optionally `streamId` to the metadata being displayed. The media route returns409 `FRAME_SUPERSEDED` if the requested identity is no longer current and returns matching `x-frame-*` headers on success. QA must correlate that identity with capture/receive timestamps and the browser's decoded-image presentation observation; a metadata refresh or server processing duration alone is not capture-to-render latency. The [camera panel](../../src/components/tracking/camera-panel.tsx) and [media route](../../app/api/tracking/frame/route.ts) are the application boundaries; physical timing evidence remains a separate QA measurement.

## Roles, transitions and data minimization

The canonical [authentication contract](../../src/server/auth/README.md) binds role and worker/device identity to the seeded account. The [incident action policy](../../src/server/incidents/actions.ts) allows administrator/operator acknowledgement, assignment, field check and follow-up; only assigned support accepts/completes support; only administrators clear hazards, authorize reopening or close incidents. Each mutation checks run and incident revisions and appends actor/time history.

The [snapshot projection](../../src/server/realtime/bus.ts) restricts worker/device sessions to their bound worker and that worker's incident guidance; it clears incident audit, global events and CCTV entries. Device sessions without a worker binding receive no worker profiles. Authorized management roles receive the management snapshot. HTTP and SSE use the same projection; the separate tracking/media endpoints retain their route-specific permissions.

Clearance requires an active incident. Reopening requires a cleared hazard and no prior reopening. Closure requires separate recorded clearance and reopening. Hazard clearance alone retains closed paths. The [database contract](../../src/server/db/README.md) describes append-only guidance, request receipts, active primary lineage and persisted history. The [guidance contract](../../src/server/guidance/README.md) describes primary deduplication and translation fallbacks. These developer documents specify behavior and cannot substitute for independent API/DB QA.

The LLM [generation boundary](../../src/server/rag/generation-types.ts) receives only action code, effective locale and retrieved procedural chunks. The [actual provider](../../src/server/rag/provider.ts) sends action/locale and reviewed explanation candidates with source identifiers; it does not send profile snapshots, worker names, birth dates, nationality or diagnoses. Profile constraints affect authoritative routing and filtered retrieval before the model call. The local model selects an evidenced reviewed candidate; the application resolves that exact bilingual text and validates freshness and semantic consistency.

## Installation and clock domains

The authoritative lockfile is `package-lock.json`, with Node22 and npm10.9.8. Two pnpm registry failures are preserved in technical setup evidence; a clean isolated npm installation was executed successfully. `ONNXRUNTIME_NODE_INSTALL_CUDA=skip` avoids downloading optional GPU assets for CPU inference. A nested Sharp override uses the patched version0.35.4; actual embedding regression remains the RAG Lead's evidence.

Scenario time is virtual. Guidance generation/expiry, document approval/validity and physical observations use UTC wall time. Mock scenario observations store virtual `observedAtMs`; their presentation timestamp is wall-now minus their virtual age, and their stale state uses virtual age. This derived timestamp is not a physical capture-time measurement and remains visibly synthetic. Virtual scenario09:00 never backdates a real knowledge review completed later. QA owns a preserved, versioned mapping of fixture virtual time to document-test wall time; actual review timestamps remain unchanged.

Phone clock synchronization uses the lowest-roundtrip of three `/api/clock` probes. The lower-bound offset is server observation time minus device response-receipt time. Corrected upload capture time is raw device capture time plus this offset, preserving a conservative bound rather than claiming exact one-way latency. `CaptureClockSchema` preserves raw device time, offset, roundtrip uncertainty and synchronization time with the frame/UWB observation. Re-synchronize on foreground return or detected clock changes. If uncertainty exceeds50ms, the frozen QA protocol requires an independent filmed-timer method or an inconclusive latency result. Details and calibration steps are in [the calibration tool guide](../../tools/calibration/README.md). Tracking snapshots emit schema1.0.1 while readers retain1.0.0 compatibility.

While active, compare elapsed UTC against elapsed monotonic time from the last calibration baseline. Effective capture uncertainty is the calibration roundtrip plus the absolute observed residual. At a residual of50ms or more, stop the current native capture/ranging session, repeat the three probes and restart with the new calibration. Check before a native camera upload as well as at controller events/polls. Smaller drift widens uncertainty and never silently clamps a future timestamp; server rejection remains explicit. This uncertainty bound and restart rule do not substitute for physical latency measurements.

The Flutter [native-device boundary](../../apps/mobile/lib/services/native_device_service.dart) owns `gs_safety/native_device` commands and `gs_safety/native_events`. It exposes actual capability/permission results, pairing preparation, UWB/camera lifecycle and failure events. Unsupported capabilities and permission failures remain explicit; a prepared session is not evidence of successful ranging. The [mobile integration guide](../../apps/mobile/README.md) describes foreground operation and links actual build/device evidence.
